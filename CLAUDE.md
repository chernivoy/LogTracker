# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Про проект

**LogTracker (ADAICA)** — Windows-only десктопний застосунок на CustomTkinter. Копіює `.log` файли з мережевої/системної теки в локальну, стежить за появою нових рядків з помилками і показує останню помилку в невеликому безрамковому вікні поверх усіх вікон, згорнутому в системний трей.

Точка входу: `logger.py` → клас `LogTrackerApp`.

## Команди

Проект без тестів, лінтерів і CI. Все запускається вручну з кореня репозиторію.

```powershell
# Віртуальне середовище (у репо є і .venv, і venv — актуальне .venv)
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt

# Запуск
python logger.py

# Збірка через spec-файл
pyinstaller logger.spec        # → dist/logger/logger.exe

# Збірка через GUI (варіант із README, дав поточний output/logger/)
pip install auto-py-to-exe
auto-py-to-exe
```

Python 3.12. `requirements.txt` збережений у UTF-16 — читати/редагувати з урахуванням кодування.

## Архітектура

### Потік даних

```
source_directory (з src/config.ini)
   │  FileHandler.copy_files_from_source_dir  — копіює нові/оновлені .log, прибирає осиротілі
   ▼
destination_directory (типово C:\temp\logger)
   │  FileChangeHandler.check_new_errors      — читає лише «хвіст» файлу з збереженого offset
   ▼
event_queue (queue.Queue з lambda-колбеків)
   │  LogTrackerApp.process_queue             — розбирає чергу в головному потоці Tk
   ▼
LogTrackerApp.on_error_found → ErrorWindow (+ підняття вікна з трею)
```

### Два незалежні таймери в main loop

`logger.py` крутить два `root.after()`-цикли, і це основний рушій застосунку:

- `process_queue()` — кожні **100 мс**, витягує колбеки з `event_queue` і виконує їх у головному потоці Tk.
- `periodic_sync()` — кожну **1000 мс**, викликає `sync_files_and_check()` (копіювання + перевірка на нові помилки).

**Важливо:** `watchdog.Observer` теж запускається (`run()`), але `FileChangeHandler.on_modified` лише друкує в консоль — виявлення помилок фактично тримається на 1-секундному полінгу, а не на watchdog-подіях. Не покладайся на watchdog як на джерело подій, не переписавши логіку. Єдиний watchdog-обробник, що впливає на стан, — `on_deleted`, і він **навмисно** знімає файл з обліку лише коли той реально зник (`os.path.exists`), інакше атомарна підміна копії ламала показ помилки (див. «Копіювання атомарне»).

**Правило потоків:** watchdog виконується в окремому потоці. Віджети Tk чіпати з нього не можна — тільки класти колбек у `event_queue`. Це причина існування черги.

### Позиційна логіка «offset»

`FileChangeHandler.file_paths` — це dict `{шлях: розмір_у_байтах}`, який слугує курсором для `file.seek()`. `read_new_lines()` читає від збереженого offset до кінця.

П'ять властивостей цього коду навмисні — не «спрощуй» їх назад:

- **Офсет береться з `file.tell()` після читання**, а не з `getsize()`, знятого до відкриття. Лог дописують безперервно, тож рядки, що потрапили у файл між цими двома моментами, читалися, але офсет за ними не встигав — і наступний тік показував ті самі помилки вдруге.
- **`errors='replace'` при відкритті.** Строгий UTF-8 кидав `UnicodeDecodeError` на будь-якому не-UTF-8 байті (напр. рядок у cp1251), офсет не рухався, і файл назавжди випадав зі спостереження.
- **Офсет оновлюється у `finally`.** Пропустити шматок при збої — відновлювано; заморозити позицію — ні.
- **Офсет більший за розмір файлу скидається в 0.** Так обробляється ротація й усічення логу.
- **Новий файл береться на облік із межею за часом** (`_adopt_if_new`). Офсет ставиться на кінець, бо читання з нуля висипало б усю історію як свіжі помилки. Але якщо `mtime` файлу не старіший за `started_at` — файл живий, і його помилки показуються: стежений застосунок заводить **новий лог на кожну сесію**, і записане туди до першого погляду трекера інакше зникало б безслідно. Ознака саме `mtime`, а не мітка в рядку (див. нижче).

Файл читається як `utf-8`, а **не** `utf-8-sig`, щоб офсети лишалися звичайними байтовими зміщеннями. Наслідок: BOM доходить до зіставлення як символ, а пробільним він не вважається, тож `str.strip()` його не прибирає — для цього є `normalize_line()`.

Рядок вважається помилкою, якщо після `normalize_line()` він **починається** зі слова з `word` (типово `ERR`).

### Вибір помилки для показу

**У вікні завжди рівно одна помилка — найактуальніша з усіх файлів.**

Порядок такий: `check_new_errors()` повертає **список** усіх помилок з нової частини файлу, `_newest_error()` порівнює їх із поточним лідером, і в чергу йде одне сповіщення `on_error_found(file_path, error_line)` з переможцем.

Порівняння — **виключно за `mtime` файлу**, а не за порядком обходу і **не за міткою часу в рядку**.

> **Мітку в рядку використовувати не можна.** Застосунок пише її в UTC, а файлова система живе за місцевим часом; різниця стала й мовчазна — на цій машині рівно 2 години (виміряно на всіх файлах). Порівняння такої мітки з `datetime.now()` оголошувало щойно записану помилку старішою за запуск трекера, і вона не показувалась узагалі. Функції `parse_line_time()` більше немає — не повертай її.

Кандидат від файлу — його **остання** помилка (лог дописується в кінець, порядок читання = порядок запису). Між файлами виграє більший `mtime`.

Щоб `mtime` був правдивим сигналом, `copy_file_without_waiting` **переносить час зміни джерела на копію** через `os.utime`. Без цього копія мала б час копіювання, за яким про момент запису судити неможливо.

Звідси й умова копіювання: `abs(mtime_джерела - mtime_копії) > 0.001`, тобто будь-яка **різниця**, а не `>`. Через `>` застарілі копії, зроблені до введення переносу mtime, не оновилися б ніколи — у них стоїть час копіювання, завідомо новіший за джерело.

Читаються при цьому **всі** нові рядки кожного файлу — інакше офсети зсунулися б повз непрочитане, і порівнювати було б нічого.

**Стартове заповнення.** `run()` робить одну синхронізацію, а тоді викликає `show_latest_known_error()` → `find_latest_existing_error()`, який читає файли **цілком** (не чіпаючи офсетів) і показує найсвіжішу вже наявну помилку. Без цього вікно лишалося порожнім аж до першої нової помилки, бо `track_files()` ставить офсети на кінець файлів і весь наявний вміст вважається переглянутим. Повний прохід дешевий: 58 файлів / 2 МБ — близько 57 мс.

Показ при старті йде з `alert=False`, тож вікно **не** піднімається з трею: це відновлення стану, а не нова подія.

**Важливо при перевірці вручну:** дописувати тестовий рядок треба в **джерело**, а не в теку призначення. Правка в теці призначення робить її новішою за джерело, `needs_copy` не спрацьовує, тік завершується з `copied=False` — і перевірка на помилки взагалі не запускається. До того ж наступне справжнє оновлення джерела затре цю правку.

### Що дозволено видаляти в теці призначення

`copy_files_from_source_dir` приймає множину `managed_files` (живе у `FileChangeHandler`) і прибирає **лише** ті файли, які скопіював сам застосунок. Тека призначення задається користувачем через UI, тож раніше сторонній `.log`, що там лежав, видалявся без попередження.

Наслідок: копії, зроблені до перезапуску, більше не прибираються — множина стартує порожньою. Це свідомий обмін: залишений застарілий файл відновлюваний, видалений чужий — ні.

Розширення файлів — параметр `file_extension`, який приходить з `config.ini`. Раніше в цій функції стояв жорсткий `'.log'`, тож зміна ключа розводила застосунок: стежив за одним, копіював інше.

### Копіювання атомарне

`copy_file_without_waiting` пише в `<ім'я>.part` і підміняє через `os.replace()`. Пряме відкриття призначення в `'wb'` обрізало його до початку читання: зрив копіювання лишав обрізаний файл із `mtime` «зараз», через що умова `getmtime(source) > getmtime(dest)` більше не спрацьовувала — копія лишалася скаліченою назавжди. Функція повертає `bool`, і `copied` виставляється лише за реальним успіхом.

Заблокований файл на тіку **пропускається**, а не очікується: `periodic_sync` повторить спробу через секунду. Блокувальний `wait_for_file()` прибраний — він тримав головний потік Tk до 2 с на файл, а файлів десятки.

**Пастка: `os.replace` дає watchdog-подію `deleted` на цільовий файл.** На Windows підміна `<ім'я>.part → <ім'я>.log` породжує подію `deleted` для `<ім'я>.log` (одразу за нею — `moved`), хоча файл не зникає. Тому `on_deleted` знімає файл з обліку **лише коли `not os.path.exists(src_path)`** — `os.replace` атомарний, ціль завжди існує, тож перевірка надійно відрізняє підміну від справжнього видалення. Без цієї перевірки кожне копіювання активного лога евіктило його з `file_paths`, наступний тік «усиновлював» його заново (`_adopt_if_new`), а усиновлення повертає **всі** наявні помилки файлу — і згорнуте в трей вікно вискакувало зі старою, вже показаною помилкою, наче з'явилася нова. Прибирання осиротілих копій на `on_deleted` не тримається — це робить `_forget_missing_files` на тіку синхронізації, тож звужена умова нічого не втрачає.

Обидва ini перелічені в `.gitignore`, але були закомічені раніше, тому зміни в них далі потрапляють у `git status`.

### DPI-конвенція (легко зламати)

CustomTkinter сам множить розміри в `root.geometry()` на свій `window_scaling` (= DPI монітора / 96), а зворотно ділить у `root.geometry()`-**геттері** та `_reverse_window_scaling()`. Тому save↔load побудовані **симетрично поверх рідної моделі CTk, без ручного множника**. В ini зберігаються **ЛОГІЧНІ** width/height і **ФІЗИЧНІ** x/y:

- **`save_window_size`** пише `_to_logical(winfo_width())` (= `winfo_width()/scale`, тобто логічну ширину) і `winfo_x()` (фізичний, надійне ціле — може бути від'ємним);
- **`load_window_size`** віддає логічні w/h у `geometry()` **як є** — CTk домножує їх до фізичних сам. Жодного `/scale` тут більше немає.

**x/y — тільки через `winfo_x()/winfo_y()`, не через розбір рядка `geometry()`.** Геттер `root.geometry()` реверсить лише w/h, але позицію Tk у рядку віддає неоднозначно: `-100` означає «100 px від правого краю», а не `x=-100`. Для мультимонітора з від'ємними координатами (сценарій Retina/RDP) це критично, тож позицію беремо цілим із `winfo_*`.

**Наслідок для зміни DPI:** оскільки зберігається логічний розмір, при реконекті RDP з іншим DPI вікно тримає той самий **логічний** розмір (виглядає пропорційно так само), а не фіксований піксельний.

**Де ще потрібен масштаб.** `WindowHandler._window_scale(root)` читає **кешоване** `root._get_window_scaling()` CTk (те саме значення, яким CTk множить `geometry()`, без Win32-виклику на подію). Він потрібен там, де код працює у фізичному просторі: `do_resize` (курсор у фізичних px → логічна `geometry()`), зона краю/мінімум ресайзу, і оцінка фізичного розміру для `clamp_to_visible` у `load_window_size`/`on_restore_defaults`. Запасний ланцюг: `rdp.get_windows_dpi_scale()` → `2.0` (усереднює `(dpi_x+dpi_y)/2`, як CTk). `_to_logical` реверсить через `root._reverse_window_scaling()` з тим самим fallback.

> **Міграція ini.** Стара версія `save_window_size` зберігала **фізичні** w/h. Після переходу на логічне зберігання наявні фізичні значення в `window_config.ini` довелося поділити на масштаб (÷2 на цій машині), інакше перший запуск домножив би їх удвічі. Далі формат самоузгоджений: будь-який `save_window_size` перепише секцію в логічних одиницях.

**DPI-awareness — рівно один раз на процес.** `logger.py` на старті виставляє `SetProcessDpiAwarenessContext(-4)` = **PER_MONITOR_AWARE_V2** (fallback: `SetProcessDpiAwareness(2)` → `SetProcessDPIAware()`) **до** створення `CTk()`. CTk у своєму `activate_high_dpi_awareness()` теж кличе `SetProcessDpiAwareness(2)`, але awareness ставиться один раз — перемагає перший виклик, і CTk-івський мовчки провалюється. Раніше тут стояв `SetProcessDpiAwareness(1)` (SYSTEM-aware, попри старий лог «PER_MONITOR»): процес «замерзав» на DPI входу, а при реконекті RDP з іншим DPI Windows віртуалізував координати (звідси від'ємні X/Y і зникле вікно), тоді як `GetDpiForMonitor` у CTk бачив реальний новий DPI — розсинхрон, що ламав і розмір, і позицію. V2 тримає координати реальними й узгодженими з масштабом CTk. (`rdp.get_window_dpi`, який теж кликав awareness(2), був мертвий — видалений.)

**`root.update()` у `create_widgets` тримає стартовий розмір (НЕ прибирати).** `ErrorWindow.create_widgets` після побудови віджетів робить `update_idletasks()` **і** `root.update()`. Другий виклик обов'язковий: він **мапить вікно на його реальному моніторі ще під час побудови**, тож CTk застосовує збережену геометрію у фізичному розмірі за DPI саме цього монітора. CTk визначає масштаб один раз при `CTk()` (`ScalingTracker.add_window` → `get_window_dpi_scaling`), коли вікно ще не спозиційоване — тобто за DPI **первинного** монітора; перший `check_dpi_scaling` уточнює масштаб лише через ~100 мс після `mainloop`. Без `root.update()` вікно мапиться аж на `mainloop`, і на моніторі з іншим DPI, ніж первинний, логічний розмір домножувався не на той масштаб — вікно відкривалося **замалим** і виправлялося тільки після ручного ресайзу (`do_resize` читає вже коректний масштаб). `update_idletasks` тут не рятує — він вікно **не** мапить. Запобіжник-дубль: `LogTrackerApp._reapply_saved_geometry` через `root.after(250, …)` у `run()` ще раз застосовує збережену геометрію, коли масштаб уже точний (no-op, якщо розмір і так правильний). Історія: ці два `update()` колись помилково скоротили до одного `update_idletasks` заради «уникнення реентрантності» — і саме це дало регресію «замалого вікна на старті».

### Запобіжник від зниклого вікна (RDP-реконект)

Головний сценарій зникнення: після реконекту RDP (особливо з Retina-клієнта зі зміною DPI/роздільної здатності) збережені координати опиняються поза новим екраном або стають від'ємними, і безрамкове вікно не видно. Три рівні захисту, усі у фізичних координатах (тих самих, у яких `winfo_*` і `GetSystemMetrics` при DPI-awareness):

- **`rdp.clamp_to_visible(x, y, w, h)`** підганяє позицію в межі **віртуального** екрана (`SM_*VIRTUALSCREEN`, тобто всі монітори; від'ємний origin додаткового монітора зберігається). Викликається в `load_window_size`, `restore_window`, `on_restore_defaults`, `stop_resize`.
- **`LogTrackerApp._ensure_on_screen`** — тік раз на 2 с, лікує **два** сліди реконекту, бо події від користувача нема: (а) якщо **відкрите** вікно повністю поза екраном (`rdp.is_rect_visible`, поріг 48 px) — повертає його всередину й піднімає; (б) відновлює `-alpha` з теми, якщо `check_dpi_scaling` у CTk на зміні DPI затер його в `1` (CTk ставить alpha=1 **після** `_set_scaling`, тож перекрити це в `_set_scaling` не можна — тільки відновити постфактум; робимо це лише коли alpha реально «поплив», без миготіння).
- **`restore_window` тепер ЗАСТОСОВУЄ** рядок з `load_window_size` (раніше результат ігнорувався, тож відновлення з трея не перепозиціонувало вікно). `on_restore_defaults` одразу `deiconify`+`lift` (Tk-операції з потоку pystray маршаляться через `root.after`), а не лишає вікно в треї до окремого «Open».

`clamp_to_visible` у `stop_resize` спрацьовує лише коли вікно фактично невидиме (`is_rect_visible`), а не «цілком уміщається» — щоб звичайний ресайз за правий/нижній край не смикав протилежну межу.

### Безрамкове вікно

`ErrorWindow.setup_window()` вмикає `overrideredirect(True)` + `-transparentcolor` + `-alpha` + `-topmost`. Наслідок — усе, що зазвичай робить ОС, реалізовано вручну в `ui/window_handler.py` через Win32-виклики `ctypes`:

- переміщення — `start_move` / `do_move` (`do_move` виходить, якщо активний `_resize_dir`: move і resize прив'язані обидва й у зоні краю смикали б вікно разом). Move-прив'язки висять на `file_label` і `main_frame`; `CTkFrame.bind`/`CTkLabel.bind` насправді вішають на внутрішній `_canvas`, який і отримує кліки по фону, тож перетяг фону заголовка працює;
- **уся смуга заголовка — зона переміщення, не ресайзу.** `change_cursor`/`start_resize` вважають зоною заголовка все, що вище `_header_bottom(root)` (верх контент-фрейму, збереженого як `root._content_frame` в `ErrorWindow.create_widgets`), і там ресайз не вмикають — вікно рухається і за текст, і за порожній фон заголовка. Наслідок: верхній край і верхні кути **не** ресайзяться (це прийнятний обмін за зручне перетягування); ресайз лишається на нижньому/бічних краях контенту та нижніх кутах;
- ресайз за 8 напрямками — `change_cursor` / `start_resize` / `do_resize` / `stop_resize`. Зона краю `border = int(20 * scale)` — **масштабується за DPI** (20 фізичних px при DPI 200% давали б лише ~10 логічних, важко влучити трекпадом через RDP). Мінімум теж фізичний: `int(300*scale) × int(min_h*scale)`, щоб збігатися з `root.minsize(...)`, яку CTk теж множить, — інакше на межі OS клампив би розмір, а x/y усе одно зсувалися б, і вікно «повзло» б. Мінімальна **висота** динамічна: `ErrorWindow.create_widgets` міряє висоту заголовка (залежить від шрифту/DPI) і додає запас під ~кілька рядків тексту, кладе результат у `root._min_height_logical`, звідки його бере і `do_resize`, і `root.minsize`. Без цього при 100 лог. заголовок з'їдав ~40 лог., і нижня грань обрізала останній рядок у полі помилки (влазило менш ніж 3 рядки). Масштаб кешується в `start_resize` (`_resize_scale`) на весь жест, `do_resize` не смикає Win32 на кожну подію і **не** друкує (раніше 6 `print` на подію роздували лог). `do_resize` лише **рахує** цільову геометрію в `root._resize_pending`, а застосовує її `_apply_resize_frame` з **тротлінгом ~60 к/с** (leading edge через `time.perf_counter`, плюс trailing-таймер `root.after(24, …)` на фінальний кадр, який `stop_resize` скасовує й застосовує). Без тротлінгу миша (~125 подій/с) змушувала б робити повний синхронний erase+repaint шаруватого вікна на кожну подію — звідси ривки, надто по RDP. Сам `_apply_resize_frame`: `geometry()` → `root.update_idletasks()` (застосувати відкладений re-layout — пересунути HWND кнопок до нового правого краю) → **завжди** `RedrawWindow(RDW_INVALIDATE|RDW_ALLCHILDREN|RDW_UPDATENOW)`. Останнє критичне для кнопок праворуч угорі: вони закріплені за правим краєм (`sticky "ne"`, колонка з `weight 0`), тож при ресайзі змінюється лише їхня **позиція**, а CTk перемальовує віджет тільки на зміні **розміру** (`_update_dimensions_event`) — пересунуті кнопки не перемальовуються й на шаруватому вікні зникають/стрибають. `update_idletasks` тут не досить: він **не** обробляє `WM_PAINT`, тому потрібен синхронний `RedrawWindow(...UPDATENOW)`. Додатковий `RDW_ERASE` вмикається **лише** на захід/північ (де рухається початок вікна): там контент їде екраном і майже-чорні згладжені краї тексту хедера (не збігаються з ключем `transparent_color="#000001"`, тож не стають прозорими) лишають слід — стирання фону його прибирає;
- клік по кутовій кнопці (згорнути/бургер) — це клік, не ресайз і не переміщення: `change_cursor`/`start_resize` виходять, якщо `"ctkbutton" in str(event.widget)` (перевірка **до** зони заголовка, бо кнопки теж у ній);
- заокруглені кути — `round_corners()` через `CreateRoundRectRgn` + `SetWindowRgn`; регіон **скидається** на час ресайзу і накладається знову в `stop_resize` (після `update_idletasks`, щоб узяти вже оновлений розмір);
- **ім'я файла в заголовку вписується під ширину** (`LogTrackerApp._fit_header_text`). `file_label` стоїть `sticky="nw"` (натуральна ширина), тож при малій ширині довге ім'я лізло під кнопки праворуч і кінець `.log` перекривався. Метод міряє реальним (масштабованим CTk) шрифтом `file_label._label` і, якщо повний текст не влазить у відстань до кнопок (`burger_button.winfo_x()`), обрізає хвіст ІМЕНІ, лишаючи `…` перед розширенням — `.log` завжди видно. Викликається в `on_error_found` і в `on_window_resize` (лише коли `event.widget is root`).

`bind_resize_events` вішає **лише** resize-хендлери на `root`. Move-прив'язки (перетягування за заголовок) ставить `ErrorWindow.bind_events` напряму на `file_label` і `main_frame`, де є прямі посилання на віджети. Раніше `bind_resize_events` ще й дублював move, шукаючи заголовок за жорстко зашитим Tk-шляхом `".!ctkframe.!ctklabel"` — крихким до зміни ієрархії віджетів; ті самі хендлери одразу перезаписувались у `bind_events`, тож lookup був зайвий і його прибрано.

### Теми

`ThemeManager.load_theme(name)` робить `importlib.import_module(f"themes.{name}_theme")` і читає з модуля `THEME_SETTINGS`. Доступні: `dark`, `light`, `custom`, `adaica_light`.

Щоб додати тему: створити `themes/<name>_theme.py` з `THEME_SETTINGS` і додати пункт у `ContextMenu._populate_menu()` (обидві гілки — з іконками і без).

**Контракт:** усі чотири теми зараз мають **ідентичний набір ключів**. `ThemeManager.update_widgets_theme()` звертається до ключів напряму, без `.get()` — відсутній ключ дасть `KeyError` при перемиканні теми. Додаючи ключ, додавай його в усі теми.

Додаючи новий стилізований віджет, треба змінити **два** місця: `ErrorWindow.create_widgets()` (початкове створення) і `ThemeManager.update_widgets_theme()` (перемикання на льоту), плюс зареєструвати віджет у словнику `widgets_to_update`.

### Ресурси і PyInstaller

`PathUtils.resource_path()` (`utils/path.py`) резолвить шляхи через `sys._MEIPASS` у зібраному вигляді і `os.path.abspath(".")` у dev. У `ui/ui_assets.py` є **дубль** тієї самої функції; там же `HEADER_ICON_PATH` уже резолвнутий, а решта констант — відносні шляхи, які резолвляться вже у викликачів (`ImageManager`, `TrayManager`). Непослідовно, але саме так це працює.

`logger.spec` виводить два списки глобами, тож нові файли підхоплюються самі:

- `datas` — глоб по `src/*` (іконки + ini) у цільову теку `'src'`;
- `hiddenimports` — глоб по `themes/*_theme.py`. **Обов'язковий**: `ThemeManager.load_theme` тягне теми через `importlib.import_module`, статичний аналіз PyInstaller такий імпорт не бачить. Без цього exe падає на старті з `ModuleNotFoundError: No module named 'themes'`.

Збірка windowed (`console=False`), іконка exe — `src/Header.ico`.

**Куди пишуться конфіги в зібраному вигляді.** Збірка однотечна (`COLLECT`), тому `sys._MEIPASS` вказує на `dist/logger/_internal` — постійну теку поруч з exe, а не на тимчасову (тимчасова була б лише при `--onefile`). Перевірено: після запуску exe `_internal/src/window_config.ini` оновлюється і зміни переживають перезапуск.

Наслідок інший: конфіг лежить усередині теки встановлення. Під `C:\Program Files` запис впаде без прав адміністратора, а перевстановлення застосунку затре налаштування користувача.

### Логування в зібраному вигляді

`rthook_logfile.py` — PyInstaller runtime hook (`runtime_hooks` у spec), який перенаправляє `sys.stdout` і `sys.stderr` у файл:

```
%LOCALAPPDATA%\LogTracker\logger.log     — поточний запуск
%LOCALAPPDATA%\LogTracker\logger.log.1   — попередній
```

Активується строго за умовою `sys.frozen and sys.stdout is None`, тобто **лише** в windowed-збірці. Запуск із сирців (`python logger.py`) і збірка з `console=True` працюють як раніше — вивід у консоль.

Деталі, які не варто ламати при правках хука:

- **`buffering=1` (line buffering) обов'язковий** — `LogTrackerApp.on_closing` завершується через `os._exit(0)`, який не скидає буфери Python; при блоковій буферизації хвіст лога губиться.
- **Ліміт `MAX_BYTES` (5 МБ)** — `WindowHandler.do_resize` друкує ~6 рядків на кожну подію руху миші, без обмеження файл росте необмежено. Після ліміту запис тихо припиняється, застосунок працює далі.
- Файл у UTF-8. `Get-Content` у Windows PowerShell 5.1 читає в ANSI і покаже кирилицю кракозябрами — читати `Get-Content ... -Encoding UTF8`.
- Весь хук обгорнутий у `try/except`, щоб збій логування не завалив старт.

Завдяки цьому виняток на старті потрапляє у файл. Без хука `console=False` дає лише діалог «Unhandled exception in script» без тексту — жодної діагностики.

Усі ресурси `src/` (іконки + ini) тепер у git. `ImageManager.get_ctk_image()` при відсутньому файлі повертає `None` мовчки, а `TrayManager` переходить на згенеровану `create_image()`-заглушку — тобто пропалий ассет не дає помилки, лише порожню іконку. Якщо іконки зникли, шукати треба саме тут.

## Життєвий цикл вікна

`WM_DELETE_WINDOW` перевизначено на `TrayManager.minimize_to_tray` — хрестик **не закриває** застосунок. Реальний вихід — `app.on_closing()` (пункти «Exit» у бургер-меню та в меню трея), який зупиняє observer, зберігає геометрію і завершується через `os._exit(0)`.

`is_window_open` — прапорець стану; коли він `False` і приходить нова помилка, `on_error_found` сам піднімає вікно з трею.

Меню трея будується заново при кожному згортанні (`minimize_to_tray`), запускається через `run_detached()`.

## Windows-only

`ctypes.windll` викликається без охорони платформи в `utils/rdp.py`, `ui/window_handler.py`, `pin.py`. Тільки `logger.py` перевіряє `sys.platform`. Крос-платформні гілки є лише у `FileHandler` (відкриття файлу, буфер обміну, показ у провіднику).

## Мертвий код

Не редагувати без потреби, не брати за приклад:

- `pin.py` — окремий демо-скрипт `RoundedWindow`, ніде не імпортується;
- `build/`, `dist/` (від `pyinstaller logger.spec`) та `output/` (від auto-py-to-exe) — артефакти збірки, у `.gitignore`.

## Мова

Коментарі й повідомлення в коді змішані: українська, російська, англійська. Логування — виключно `print()`, без модуля `logging`. Дотримуйся стилю файлу, який редагуєш.

`logger.py` на старті виставляє `errors="replace"` для `sys.stdout` / `sys.stderr`. Без цього `print()` з кирилицею падав з `UnicodeEncodeError` на консолі в cp1252/cp866 — найчастіше всередині `except`-гілки, через що обробник помилки сам ставав помилкою і ховав початкову причину. Кодування навмисно не підміняється на utf-8: у консолях зі старою кодовою сторінкою це дало б кракозябри. У windowed-збірці вивід перехоплює `rthook_logfile.py` і пише в utf-8 без втрат.
