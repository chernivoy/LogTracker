# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Про проект

**LogTracker (ADAICA)** — Windows-only десктопний застосунок на CustomTkinter. Копіює `.log` файли з мережевої/системної теки в локальну, стежить за появою нових рядків з помилками і показує останню помилку в невеликому безрамковому вікні поверх усіх вікон, згорнутому в системний трей.

Точка входу: `logger.py` → клас `LogTrackerApp`.

## Команди

Проект без тестів, лінтерів і CI. Все запускається вручну з кореня репозиторію.

```powershell
# Віртуальне середовище (у репо є і .venv, і venv — актуальне .venv)
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt

# Запуск
python logger.py

# Збірка через spec-файл (one-file)
pyinstaller logger.spec        # → dist/logger.exe (один самодостатній файл)

# Збірка через GUI (варіант із README, дав поточний output/logger/)
pip install auto-py-to-exe
auto-py-to-exe
```

Python 3.12. `requirements.txt` збережений у UTF-16 — читати/редагувати з урахуванням кодування.

## Архітектура

### Потік даних

```
source_directory (з src/config.ini)
   │  FileHandler.copy_files_from_source_dir  — копіює нові/оновлені .log, прибирає осиротілі
   ▼
destination_directory (типово C:\temp\logger)
   │  FileChangeHandler.check_new_errors      — читає лише «хвіст» файлу з збереженого offset
   ▼
event_queue (queue.Queue з lambda-колбеків)
   │  LogTrackerApp.process_queue             — розбирає чергу в головному потоці Tk
   ▼
LogTrackerApp.on_error_found → ErrorWindow (+ підняття вікна з трею)
```

### Два незалежні таймери в main loop

`logger.py` крутить два `root.after()`-цикли, і це основний рушій застосунку:

- `process_queue()` — кожні **100 мс**, витягує колбеки з `event_queue` і виконує їх у головному потоці Tk.
- `periodic_sync()` — кожну **1000 мс**, викликає `sync_files_and_check()` (копіювання + перевірка на нові помилки).

**Важливо:** `watchdog.Observer` теж запускається (`run()`), але `FileChangeHandler.on_modified` лише друкує в консоль — виявлення помилок фактично тримається на 1-секундному полінгу, а не на watchdog-подіях. Не покладайся на watchdog як на джерело подій, не переписавши логіку. Єдиний watchdog-обробник, що впливає на стан, — `on_deleted`, і він **навмисно** знімає файл з обліку лише коли той реально зник (`os.path.exists`), інакше атомарна підміна копії ламала показ помилки (див. «Копіювання атомарне»).

**Правило потоків:** watchdog виконується в окремому потоці. Віджети Tk чіпати з нього не можна — тільки класти колбек у `event_queue`. Це причина існування черги.

### Позиційна логіка «offset»

`FileChangeHandler.file_paths` — це dict `{шлях: розмір_у_байтах}`, який слугує курсором для `file.seek()`. `read_new_lines()` читає від збереженого offset до кінця.

П'ять властивостей цього коду навмисні — не «спрощуй» їх назад:

- **Офсет береться з `file.tell()` після читання**, а не з `getsize()`, знятого до відкриття. Лог дописують безперервно, тож рядки, що потрапили у файл між цими двома моментами, читалися, але офсет за ними не встигав — і наступний тік показував ті самі помилки вдруге.
- **`errors='replace'` при відкритті.** Строгий UTF-8 кидав `UnicodeDecodeError` на будь-якому не-UTF-8 байті (напр. рядок у cp1251), офсет не рухався, і файл назавжди випадав зі спостереження.
- **Офсет оновлюється у `finally`.** Пропустити шматок при збої — відновлювано; заморозити позицію — ні.
- **Офсет більший за розмір файлу скидається в 0.** Так обробляється ротація й усічення логу.
- **Новий файл береться на облік із межею за часом** (`_adopt_if_new`). Офсет ставиться на кінець, бо читання з нуля висипало б усю історію як свіжі помилки. Але якщо `mtime` файлу не старіший за `started_at` — файл живий, і його помилки показуються: стежений застосунок заводить **новий лог на кожну сесію**, і записане туди до першого погляду трекера інакше зникало б безслідно. Ознака саме `mtime`, а не мітка в рядку (див. нижче).

Файл читається як `utf-8`, а **не** `utf-8-sig`, щоб офсети лишалися звичайними байтовими зміщеннями. Наслідок: BOM доходить до зіставлення як символ, а пробільним він не вважається, тож `str.strip()` його не прибирає — для цього є `normalize_line()`.

Рядок вважається помилкою, якщо після `normalize_line()` він **починається** зі слова з `word` (типово `ERR`).

### Вибір помилки для показу

**У вікні завжди рівно одна помилка — найактуальніша з усіх файлів.**

Порядок такий: `check_new_errors()` повертає **список** усіх помилок з нової частини файлу, `_newest_error()` порівнює їх із поточним лідером, і в чергу йде одне сповіщення `on_error_found(file_path, error_line)` з переможцем.

Порівняння — **виключно за `mtime` файлу**, а не за порядком обходу і **не за міткою часу в рядку**.

> **Мітку в рядку використовувати не можна.** Застосунок пише її в UTC, а файлова система живе за місцевим часом; різниця стала й мовчазна — на цій машині рівно 2 години (виміряно на всіх файлах). Порівняння такої мітки з `datetime.now()` оголошувало щойно записану помилку старішою за запуск трекера, і вона не показувалась узагалі. Функції `parse_line_time()` більше немає — не повертай її.

Кандидат від файлу — його **остання** помилка (лог дописується в кінець, порядок читання = порядок запису). Між файлами виграє більший `mtime`.

Щоб `mtime` був правдивим сигналом, `copy_file_without_waiting` **переносить час зміни джерела на копію** через `os.utime`. Без цього копія мала б час копіювання, за яким про момент запису судити неможливо.

Звідси й умова копіювання: `abs(mtime_джерела - mtime_копії) > 0.001`, тобто будь-яка **різниця**, а не `>`. Через `>` застарілі копії, зроблені до введення переносу mtime, не оновилися б ніколи — у них стоїть час копіювання, завідомо новіший за джерело.

Читаються при цьому **всі** нові рядки кожного файлу — інакше офсети зсунулися б повз непрочитане, і порівнювати було б нічого.

**Стартове заповнення.** `run()` делегує стартовий показ у `_refresh_startup_view()`: якщо шляхи не налаштовані — показує підказку (див. «Перший запуск і незадані шляхи»), інакше робить одну синхронізацію і викликає `show_latest_known_error()` → `find_latest_existing_error()`, який читає файли **цілком** (не чіпаючи офсетів) і показує найсвіжішу вже наявну помилку. Без цього вікно лишалося порожнім аж до першої нової помилки, бо `track_files()` ставить офсети на кінець файлів і весь наявний вміст вважається переглянутим. Повний прохід дешевий: 58 файлів / 2 МБ — близько 57 мс. `show_latest_known_error()` повертає `bool` (чи було що показати); якщо ні — `_refresh_startup_view` чистить поле, щоб не лишалась стара підказка.

Показ при старті йде з `alert=False`, тож вікно **не** піднімається з трею: це відновлення стану, а не нова подія.

**Важливо при перевірці вручну:** дописувати тестовий рядок треба в **джерело**, а не в теку призначення. Правка в теці призначення робить її новішою за джерело, `needs_copy` не спрацьовує, тік завершується з `copied=False` — і перевірка на помилки взагалі не запускається. До того ж наступне справжнє оновлення джерела затре цю правку.

### Перший запуск і незадані шляхи

На новій машині обидва шляхи в `src/config.ini` **порожні** (сід очищено — див. «Сідування»), тож застосунок мусить стартувати без них і не крашитись. Ключові запобіжники (не «спрощувати» назад):

- **observer НЕ планують на невалідну теку.** `run()` створює `Observer` і `start()`-ить його **без жодного watch**, а watch додає `_watch_destination()` — і лише коли `destination_directory` це реальна тека. Порожній/неіснуючий шлях не плануємо: емітер `ReadDirectoryChangesW` відкрив би `CreateFileW('')` і впав. `_watch_destination` робить `unschedule_all()` + `schedule(...)`, тож той самий метод годиться і для переналаштування на льоту.
- **Захист від порожнього шляху в самих операціях.** `copy_files_from_source_dir` віддає `False` одразу, якщо джерело порожнє/неіснуюче або призначення порожнє — інакше `os.listdir('')` кидає на Windows (а на POSIX мовчки лістить робочу теку), і `os.path.join('', name)` дає відносний шлях, тобто копіювання **в CWD процесу**. `track_files` і `create_directory_if_not_exists` — теж no-op на порожньому/неіснуючому шляху. Тож `periodic_sync` при незаданих шляхах стає дешевим no-op, без спаму в лог.
- **Підказка замість порожнього вікна.** `_refresh_startup_view()` дивиться `_paths_configured()` (джерело мусить **існувати**; призначення досить непорожнього — його створять) і при незаданих шляхах кладе в поле `_show_setup_hint()` — текст `Paths are not set. Open "Path settings"…`. Інакше — sync + `show_latest_known_error()`, а якщо помилок ще нема — чистить поле (`_set_error_text("")`).

Зашитий у config.ini шлях із чужої машини (напр. `...\ichernevoy`) на новому ПК не існує → `_paths_configured()` це ловить через `os.path.isdir` і теж показує підказку, а не «мовчазно нічого».

### Що дозволено видаляти в теці призначення

`copy_files_from_source_dir` приймає множину `managed_files` (живе у `FileChangeHandler`) і прибирає **лише** ті файли, які скопіював сам застосунок. Тека призначення задається користувачем через UI, тож раніше сторонній `.log`, що там лежав, видалявся без попередження.

Наслідок: копії, зроблені до перезапуску, більше не прибираються — множина стартує порожньою. Це свідомий обмін: залишений застарілий файл відновлюваний, видалений чужий — ні.

Розширення файлів — параметр `file_extension`, який приходить з `config.ini`. Раніше в цій функції стояв жорсткий `'.log'`, тож зміна ключа розводила застосунок: стежив за одним, копіював інше.

### Копіювання атомарне

`copy_file_without_waiting` пише в `<ім'я>.part` і підміняє через `os.replace()`. Пряме відкриття призначення в `'wb'` обрізало його до початку читання: зрив копіювання лишав обрізаний файл із `mtime` «зараз», через що умова `getmtime(source) > getmtime(dest)` більше не спрацьовувала — копія лишалася скаліченою назавжди. Функція повертає `bool`, і `copied` виставляється лише за реальним успіхом.

Заблокований файл на тіку **пропускається**, а не очікується: `periodic_sync` повторить спробу через секунду. Блокувальний `wait_for_file()` прибраний — він тримав головний потік Tk до 2 с на файл, а файлів десятки.

**Пастка: `os.replace` дає watchdog-подію `deleted` на цільовий файл.** На Windows підміна `<ім'я>.part → <ім'я>.log` породжує подію `deleted` для `<ім'я>.log` (одразу за нею — `moved`), хоча файл не зникає. Тому `on_deleted` знімає файл з обліку **лише коли `not os.path.exists(src_path)`** — `os.replace` атомарний, ціль завжди існує, тож перевірка надійно відрізняє підміну від справжнього видалення. Без цієї перевірки кожне копіювання активного лога евіктило його з `file_paths`, наступний тік «усиновлював» його заново (`_adopt_if_new`), а усиновлення повертає **всі** наявні помилки файлу — і згорнуте в трей вікно вискакувало зі старою, вже показаною помилкою, наче з'явилася нова. Прибирання осиротілих копій на `on_deleted` не тримається — це робить `_forget_missing_files` на тіку синхронізації, тож звужена умова нічого не втрачає.

### Конфігурація — два різні файли

| Файл | Що містить | Хто читає/пише |
|---|---|---|
| `src/config.ini` | `[Settings]`: `word`, `file_extension`, `source_directory`, `destination_directory` | `constants.CONFIG_PATH`, `SettingsPanel._save` |
| `src/window_config.ini` | `[Window]` (геометрія), `[Theme] current` | `ConfigManager`, `WindowHandler`, `ThemeManager` |

`ConfigManager.save_config()` за замовчуванням пише саме у **window_config.ini** — його дефолтний аргумент `config_file=CONFIG_FILE_WINDOW`. Налаштування шляхів зберігаються окремим кодом у `SettingsPanel._save`, який пише напряму в `CONFIG_PATH`. Перед записом `_save` **валідує й нормалізує** шляхи, а після — застосовує їх наживо через `LogTrackerApp.apply_directory_settings`, тож зміна теки діє **без перезапуску** (див. «Панель налаштування шляхів»).

Секції `[Window_path]` більше немає: вона тримала геометрію окремого вікна налаштувань, якого не існує — налаштування шляхів тепер живуть у головному вікні.

Обидва ini перелічені в `.gitignore`, але були закомічені раніше, тому зміни в них далі потрапляють у `git status`.

### Панель налаштування шляхів (SettingsPanel)

Налаштування шляхів — це **рядок контролів унизу головного вікна** (`ui/settings_panel.py`), а не окреме вікно. Пункт «Path settings» бургер-меню кличе `LogTrackerApp.open_path_settings()` → `ErrorWindow.settings_panel.open()`: панель стає в `main_frame` рядком **2** (під `error_frame`), а вікно на час показу росте рівно на її висоту. Save (успішний) і Cancel ховають панель і повертають попередню висоту.

Раніше це було модальне вікно (`ui/settings_window.py`, `grab_set`): власна геометрія в `[Window_path]`, іконка заголовка, автозбереження позиції, кламп у видимий екран — цілий другий життєвий цикл вікна заради двох полів. Файл видалено, `_PathTooltip`, `_validate` і збереження перенесені в панель як є.

Що тут навмисне:

- **Вікно РОСТЕ, а не тиснеться.** Поле помилки лишається того самого розміру: панель будується поза grid, міряється (`_measure_extra` → `winfo_reqheight` фізичний, ділимо на масштаб, додаємо нижній `_CONTENT_INSET`), і лише потім вікно збільшується й панель стає в grid. Якби порядок був зворотним, перший кадр показав би панель, втиснуту в поточну висоту за рахунок поля.
- **Приріст живе в `root._panel_extra_logical`** (0, коли панель закрита) — і це не локальна змінна, бо число потрібне чотирьом місцям поза панеллю:
  - `WindowHandler.min_height_logical(root)` = `_min_height_logical` + приріст. Звідси беруть межу і `root.minsize`, і ручний ресайз у `do_resize`. Розійшлися б вони — при ресайзі з півночі/заходу OS клампив би розмір по одній межі, а x/y зсувалися б по іншій, і вікно «повзло» б;
  - `ErrorWindow.apply_dynamic_min_height` (його повторно кличе `logger.run` через `after`) виставляє `minsize` теж через цю суму — інакше зняв би запас під відкриту панель;
  - `save_window_size` приріст **віднімає**: в ini має лежати ВЛАСНА висота користувача, інакше закриття панелі повернуло б розмір вікна, а збережений лишився б з нею;
  - `load_window_size` **додає** назад — відновлення з трея з відкритою панеллю інакше підрізало б вікно на її висоту.
- **Згортання рахується від ПОТОЧНОЇ висоти** (`висота - приріст`), а не повертає запам'ятану: вікно можна ресайзити й з відкритою панеллю.
- **Позиція.** Вікно росте вниз і згортається знизу, тож зазвичай її чіпати не треба. Виняток — коли на відкритті `clamp_to_visible` підняв вікно, бо панель не влазила в екран: це вимушене підняття, а не переміщення, якого хотів користувач, і без повернення назад кожне відкриття налаштувань підганяло б вікно вгору (виміряно: y 2168 → 1876 і назавжди). Тому `_expand` запам'ятовує пару «звідки, куди», а `_collapse` (через `_restore_position`) повертає вікно — **лише** якщо воно й досі стоїть там, куди його посунув кламп: якщо користувач тим часом перетягнув вікно сам, його позиція остання.
- **Логічні розміри рахуються з ОКРУГЛЕННЯМ** (`SettingsPanel._logical`), а не через `WindowHandler._to_logical` з його `int()`: панель відкривають десятки разів за сесію, і зрізаний на кожному циклі піксель накопичувався б — вікно повзло б у меншу сторону.
- **Валідація перед записом.** `_validate()`: `.strip()` + зняття лапок навколо вставленого шляху; джерело мусить існувати (`isdir`), призначення — непорожнє й не наявний файл; `source != destination` (через `normcase(abspath(...))`). Помилка йде в рядок статусу (фіксований `_ERROR_COLOR` — **НЕ** з теми, щоб не роздувати theme-контракт), панель лишається відкритою, некоректні значення в config не потрапляють. Рядок статусу постійно на місці (порожній) і в **один** рядок без `wraplength`: поява повідомлення не має міняти висоту панелі, під яку вже розсунуте вікно.
- **Застосування наживо.** `_save` після запису config ховає панель і кличе `app.apply_directory_settings(source, destination)`. Джерело підхоплюється саме (його щотіка читає `periodic_sync`), а от теку призначення тримають закешованою **два** місця — `FileChangeHandler.destination_directory` і watchdog-observer, — тож зміну призначення `apply_directory_settings` проводить вручну: оновлює обробник, `create_directory_if_not_exists`, скидає `file_paths`/`managed_files`/`last_error_file`, `track_files()`, перепланує observer через `_watch_destination()` і оновлює вікно (`_refresh_startup_view`). Без цього нова тека призначення діяла б лише після перезапуску.
- **Фіксовані висоти віджетів** (`_LABEL_HEIGHT`/`_FIELD_HEIGHT`, а не дефолтні 28 у CTk): панель розсуває вікно рівно на свою висоту, тож що компактніша смуга — то менше смикається вікно (виміряно: 166 логічних px). Заразом виміряний приріст не залежить від кегля теми, тобто лишається чинним після `apply_theme`.
- **Кнопка Browse** біля кожного поля — нативний `filedialog.askdirectory` (стартує з поточної теки, вписує `os.path.normpath`). Танцю `grab_release()`/`grab_set()` більше нема: панель не модальна, локального граба, який перехопив би фокус у вікна ОС, не існує. Діалог належить головному вікну (`parent=root`) і показується **над** ним, попри `-topmost` (перевірено).
- **Тултіп повного шляху** при наведенні на поле — `_PathTooltip` (у CTk вбудованих тултіпів нема). Читає `entry.get()` свіжим на кожне наведення. Шрифт — **не** сирий кортеж `("Inter", 13)` (Tk трактує його як пункти й домножує на DPI → на high-DPI завелико), а вже масштабований піксельний спек із `entry._entry.cget("font")` (напр. `"Inter -26"`); фолбек — `-round(base*scale)` через `WindowHandler._window_scale`.
- **Клавіатура.** Enter — Save, Escape — Cancel; прив'язки ставляться на `root` (подія з поля піднімається bindtags до свого toplevel) **без** `add="+"` і знімаються при закритті: більше ці дві клавіші на головному вікні не слухає ніхто. Фокус у перше поле віддає `_focus_first`, і `focus_force` там обов'язковий — вікно безрамкове, і після закриття бургер-меню фокус до нього сам не повертається.
- **Волосяний сепаратор** над контролями кольором `settings_entry_border_color`: у dark поле помилки прозоре й без рамки, тож без лінії панель просто зависала б у вікні. Фон самої панелі — `"transparent"`, тобто те, що реально рендерить `main_frame` (у dark це `gray14`, той самий колір, який окремо прописаний у `settings_bg`).
- **Тему можна перемкнути, не закриваючи панель** — бургер-меню поруч і більше нічим не заблоковане. Тому, на відміну від колишнього модального вікна, стилю «один раз при відкритті» не досить: `LogTrackerApp.toggle_theme` кличе `settings_panel.apply_theme()`, який перефарбовує відкриту панель наживо (no-op, коли вона закрита). У `widgets_to_update` панель не входить — її віджетів більшість часу не існує, а `update_widgets_theme` читає ключі напряму.

### DPI-конвенція (легко зламати)

CustomTkinter сам множить розміри в `root.geometry()` на свій `window_scaling` (= DPI монітора / 96), а зворотно ділить у `root.geometry()`-**геттері** та `_reverse_window_scaling()`. Тому save↔load побудовані **симетрично поверх рідної моделі CTk, без ручного множника**. В ini зберігаються **ЛОГІЧНІ** width/height і **ФІЗИЧНІ** x/y:

- **`save_window_size`** пише `_to_logical(winfo_width())` (= `winfo_width()/scale`, тобто логічну ширину) і `winfo_x()` (фізичний, надійне ціле — може бути від'ємним);
- **`load_window_size`** віддає логічні w/h у `geometry()` **як є** — CTk домножує їх до фізичних сам. Жодного `/scale` тут більше немає.

**x/y — тільки через `winfo_x()/winfo_y()`, не через розбір рядка `geometry()`.** Геттер `root.geometry()` реверсить лише w/h, але позицію Tk у рядку віддає неоднозначно: `-100` означає «100 px від правого краю», а не `x=-100`. Для мультимонітора з від'ємними координатами (сценарій Retina/RDP) це критично, тож позицію беремо цілим із `winfo_*`.

**Наслідок для зміни DPI:** оскільки зберігається логічний розмір, при реконекті RDP з іншим DPI вікно тримає той самий **логічний** розмір (виглядає пропорційно так само), а не фіксований піксельний.

**Де ще потрібен масштаб.** `WindowHandler._window_scale(root)` читає **кешоване** `root._get_window_scaling()` CTk (те саме значення, яким CTk множить `geometry()`, без Win32-виклику на подію). Він потрібен там, де код працює у фізичному просторі: `do_resize` (курсор у фізичних px → логічна `geometry()`), зона краю/мінімум ресайзу, і оцінка фізичного розміру для `clamp_to_visible` у `load_window_size`/`on_restore_defaults`. Запасний ланцюг: `rdp.get_windows_dpi_scale()` → `2.0` (усереднює `(dpi_x+dpi_y)/2`, як CTk). `_to_logical` реверсить через `root._reverse_window_scaling()` з тим самим fallback.

> **Міграція ini.** Стара версія `save_window_size` зберігала **фізичні** w/h. Після переходу на логічне зберігання наявні фізичні значення в `window_config.ini` довелося поділити на масштаб (÷2 на цій машині), інакше перший запуск домножив би їх удвічі. Далі формат самоузгоджений: будь-який `save_window_size` перепише секцію в логічних одиницях.

**DPI-awareness — рівно один раз на процес.** `logger.py` на старті виставляє `SetProcessDpiAwarenessContext(-4)` = **PER_MONITOR_AWARE_V2** (fallback: `SetProcessDpiAwareness(2)` → `SetProcessDPIAware()`) **до** створення `CTk()`. CTk у своєму `activate_high_dpi_awareness()` теж кличе `SetProcessDpiAwareness(2)`, але awareness ставиться один раз — перемагає перший виклик, і CTk-івський мовчки провалюється. Раніше тут стояв `SetProcessDpiAwareness(1)` (SYSTEM-aware, попри старий лог «PER_MONITOR»): процес «замерзав» на DPI входу, а при реконекті RDP з іншим DPI Windows віртуалізував координати (звідси від'ємні X/Y і зникле вікно), тоді як `GetDpiForMonitor` у CTk бачив реальний новий DPI — розсинхрон, що ламав і розмір, і позицію. V2 тримає координати реальними й узгодженими з масштабом CTk. (`rdp.get_window_dpi`, який теж кликав awareness(2), був мертвий — видалений.)

**`root.update()` у `create_widgets` тримає стартовий розмір (НЕ прибирати).** `ErrorWindow.create_widgets` після побудови віджетів робить `update_idletasks()` **і** `root.update()`. Другий виклик обов'язковий: він **мапить вікно на його реальному моніторі ще під час побудови**, тож CTk застосовує збережену геометрію у фізичному розмірі за DPI саме цього монітора. CTk визначає масштаб один раз при `CTk()` (`ScalingTracker.add_window` → `get_window_dpi_scaling`), коли вікно ще не спозиційоване — тобто за DPI **первинного** монітора; перший `check_dpi_scaling` уточнює масштаб лише через ~100 мс після `mainloop`. Без `root.update()` вікно мапиться аж на `mainloop`, і на моніторі з іншим DPI, ніж первинний, логічний розмір домножувався не на той масштаб — вікно відкривалося **замалим** і виправлялося тільки після ручного ресайзу (`do_resize` читає вже коректний масштаб). `update_idletasks` тут не рятує — він вікно **не** мапить. Запобіжник-дубль: `LogTrackerApp._reapply_saved_geometry` через `root.after(250, …)` у `run()` ще раз застосовує збережену геометрію, коли масштаб уже точний (no-op, якщо розмір і так правильний). Історія: ці два `update()` колись помилково скоротили до одного `update_idletasks` заради «уникнення реентрантності» — і саме це дало регресію «замалого вікна на старті».

### Запобіжник від зниклого вікна (RDP-реконект)

Головний сценарій зникнення: після реконекту RDP (особливо з Retina-клієнта зі зміною DPI/роздільної здатності) збережені координати опиняються поза новим екраном або стають від'ємними, і безрамкове вікно не видно. Три рівні захисту, усі у фізичних координатах (тих самих, у яких `winfo_*` і `GetSystemMetrics` при DPI-awareness):

- **`rdp.clamp_to_visible(x, y, w, h)`** підганяє позицію в межі **віртуального** екрана (`SM_*VIRTUALSCREEN`, тобто всі монітори; від'ємний origin додаткового монітора зберігається). Викликається в `load_window_size`, `restore_window`, `on_restore_defaults`, `stop_resize`.
- **`LogTrackerApp._ensure_on_screen`** — тік раз на 2 с, лікує **два** сліди реконекту, бо події від користувача нема: (а) якщо **відкрите** вікно повністю поза екраном (`rdp.is_rect_visible`, поріг 48 px) — повертає його всередину й піднімає; (б) відновлює `-alpha` з теми, якщо `check_dpi_scaling` у CTk на зміні DPI затер його в `1` (CTk ставить alpha=1 **після** `_set_scaling`, тож перекрити це в `_set_scaling` не можна — тільки відновити постфактум; робимо це лише коли alpha реально «поплив», без миготіння).
- **`restore_window` тепер ЗАСТОСОВУЄ** рядок з `load_window_size` (раніше результат ігнорувався, тож відновлення з трея не перепозиціонувало вікно). `on_restore_defaults` одразу `deiconify`+`lift` (Tk-операції з потоку pystray маршаляться через `root.after`), а не лишає вікно в треї до окремого «Open».

`clamp_to_visible` у `stop_resize` спрацьовує лише коли вікно фактично невидиме (`is_rect_visible`), а не «цілком уміщається» — щоб звичайний ресайз за правий/нижній край не смикав протилежну межу.

### Безрамкове вікно

`ErrorWindow.setup_window()` вмикає `overrideredirect(True)` + `-transparentcolor` + `-alpha` + `-topmost`. Наслідок — усе, що зазвичай робить ОС, реалізовано вручну в `ui/window_handler.py` через Win32-виклики `ctypes`:

- переміщення — `start_move` / `do_move` (`do_move` виходить, якщо активний `_resize_dir`: move і resize прив'язані обидва й у зоні краю смикали б вікно разом). Move-прив'язки висять на `file_label` і `main_frame`; `CTkFrame.bind`/`CTkLabel.bind` насправді вішають на внутрішній `_canvas`, який і отримує кліки по фону, тож перетяг фону заголовка працює;
- **уся смуга заголовка — зона переміщення, не ресайзу.** `change_cursor`/`start_resize` вважають зоною заголовка все, що вище `_header_bottom(root)` (верх контент-фрейму, збереженого як `root._content_frame` в `ErrorWindow.create_widgets`), і там ресайз не вмикають — вікно рухається і за текст, і за порожній фон заголовка. Наслідок: верхній край і верхні кути **не** ресайзяться (це прийнятний обмін за зручне перетягування); ресайз лишається на нижньому/бічних краях контенту та нижніх кутах;
- ресайз за 8 напрямками — `change_cursor` / `start_resize` / `do_resize` / `stop_resize`. Зона краю `border = int(20 * scale)` — **масштабується за DPI** (20 фізичних px при DPI 200% давали б лише ~10 логічних, важко влучити трекпадом через RDP). Мінімум теж фізичний: `int(300*scale) × int(min_h*scale)`, щоб збігатися з `root.minsize(...)`, яку CTk теж множить, — інакше на межі OS клампив би розмір, а x/y усе одно зсувалися б, і вікно «повзло» б. Мінімальна **висота** динамічна: `ErrorWindow.create_widgets` міряє висоту заголовка (залежить від шрифту/DPI) і додає запас під ~кілька рядків тексту, кладе результат у `root._min_height_logical`, звідки його бере і `do_resize`, і `root.minsize`. Без цього при 100 лог. заголовок з'їдав ~40 лог., і нижня грань обрізала останній рядок у полі помилки (влазило менш ніж 3 рядки). Масштаб кешується в `start_resize` (`_resize_scale`) на весь жест, `do_resize` не смикає Win32 на кожну подію і **не** друкує (раніше 6 `print` на подію роздували лог). `do_resize` лише **рахує** цільову геометрію в `root._resize_pending`, а застосовує її `_apply_resize_frame` з **тротлінгом ~60 к/с** (leading edge через `time.perf_counter`, плюс trailing-таймер `root.after(24, …)` на фінальний кадр, який `stop_resize` скасовує й застосовує). Без тротлінгу миша (~125 подій/с) змушувала б робити повний синхронний erase+repaint шаруватого вікна на кожну подію — звідси ривки, надто по RDP. Сам `_apply_resize_frame`: `geometry()` → **`root.update()`** (застосувати відкладений re-layout — пересунути HWND кнопок до нового правого краю) → **завжди** `RedrawWindow(RDW_INVALIDATE|RDW_ALLCHILDREN|RDW_UPDATENOW)` → **ще один `root.update()`**.

> **Два `update()` на кадр — не зайві, це і є «намальований кадр».** Перший мусить бути саме `update()`, а не `update_idletasks()`: про новий розмір Tk дізнається з `ConfigureNotify`, а це **звичайна** подія, не idle-таск, тож `update_idletasks` її не забирає. Без цього кадр малювався зі **старою розкладкою** на вже новому вікні (намальований контур і кнопки відставали від справжнього краю на кадр), та й `winfo_*` нижче були б застарілі — під них лягав би й **регіон**. Другий `update()` потрібен, бо `RedrawWindow(...UPDATENOW)` лише **розсилає** `WM_PAINT`, а Tk перетворює його на свою подію `Expose` і малює вже у власному циклі подій: без прокрутки циклу край вікна лишався без рамки, а нижній/правий кут — без округлення. Виміряно (кадр ресайзу проти чесної повної перемальовки того самого розміру, 20 кадрів): `update_idletasks` без фінального `update` — ~573k відмінних пікселів, лише перший `update` — ~272k, обидва — **рівно 0**. Ціна: повний жест став ~на 50% довшим за стінним годинником (кадри тепер справді малюються, а не відкладаються), тож `_apply_resize_frame` ще й **пропускає кадр із незміненою геометрією** (`root._resize_applied`) — миша сипле подіями і на тремтінні в межах пікселя, а трейлінг-таймер приходить із тим самим рядком, що вже намальований.
>
> Оскільки `update()` прокручує чергу подій, звідти може прилетіти новий `<B1-Motion>` → `do_resize` → знову `_apply_resize_frame`. Від рекурсії боронить прапорець `root._resize_painting`: вкладений виклик лише оновлює `_resize_pending`, а малює його зовнішній кадр — і малює вже новішу ціль.

`RedrawWindow` критичний для кнопок праворуч угорі: вони закріплені за правим краєм (`sticky "ne"`, колонка з `weight 0`), тож при ресайзі змінюється лише їхня **позиція**, а CTk перемальовує віджет тільки на зміні **розміру** (`_update_dimensions_event`) — пересунуті кнопки не перемальовуються й на шаруватому вікні зникають/стрибають. Самої прокрутки циклу подій тут не досить: `WM_PAINT` вона дітям не розсилає, тому потрібен синхронний `RedrawWindow(...UPDATENOW)`. Додатковий `RDW_ERASE` вмикається **лише** на захід/північ (де рухається початок вікна): там контент їде екраном і майже-чорні згладжені краї тексту хедера (не збігаються з ключем `transparent_color="#000001"`, тож не стають прозорими) лишають слід — стирання фону його прибирає. На схід/південь erase не додає чистоти (виміряно), лише мерехтіння.
- клік по кутовій кнопці (згорнути/бургер) — це клік, не ресайз і не переміщення: `change_cursor`/`start_resize` виходять, якщо `"ctkbutton" in str(event.widget)` (перевірка **до** зони заголовка, бо кнопки теж у ній);
- заокруглені кути — `round_corners()` → `_set_corner_region()` через `CreateRoundRectRgn` + `SetWindowRgn`. Радіус `WindowHandler.CORNER_RADIUS` (15) — **логічний**, а фізичний дає `_outline_radius_px(root)`: він питає радіус у **самого CTk** — `root._outline_frame._apply_widget_scaling(CORNER_RADIUS)`, округлене так само, як округлює `DrawEngine`. (Логічний радіус можна перекрити атрибутом `root._outline_radius` поруч із `_outline_frame` — так робить попап бургер-меню, у якого картка менша й радіус свій, 10. Пара «віджет + радіус» лишається на одному вікні, тож розійтися не може.) Тобто регіон і намальована рамка беруть **одне й те саме число з одного джерела** (`_outline_frame` ставить `ErrorWindow.create_widgets`). **Своїм перерахунком радіус більше не рахується — і не має.** Раніше тут стояло `CORNER_RADIUS * _window_scale(root)`, тобто **віконний** масштаб CTk, тоді як дугу CTk малює за **віджетним**. У сталому стані обидва рівні (спільний `window_dpi_scaling_dict[root]`), але читаються в різні моменти й оновлюються різними подіями — і при зміні DPI розходяться: у полі спіймано регіон з радіусом 15 при дузі 30. Виглядає це як **дві дуги в кожному куті** — жорсткий зріз регіону по малому радіусу, намальована рамка по великому, а між ними смуга фону вікна без жодної межі. **Останні два аргументи `CreateRoundRectRgn` — це розмір ЕЛІПСА кута (діаметр), а не радіус**, тож `_set_corner_region` подвоює значення. Раніше константа була `30` і йшла у Win32 як є — фактичний радіус усе одно виходив 15, просто число брехало вдвічі; вигляд вікна від виправлення не змінився. Це важливо тепер, коли те саме число дістає `main_frame` як `corner_radius` (див. «Контур вікна»): якби воно означало різне по різні боки, намальована рамка пройшла б повз межу обрізання. Регіон тримається **живим під час ресайзу**: `_apply_resize_frame` перераховує його щокадру під новий фізичний розмір (`redraw=False` — малює наступний `RedrawWindow`), тож кути лишаються скругленими протягом усього жесту; раніше `start_resize` знімав регіон (`SetWindowRgn(hwnd, 0)`) і кути ставали квадратними аж до `stop_resize`. Перерахунок працює, бо регіон завжди зроблено з поточного `winfo_*` **після `update()`** — тобто вже після того, як Tk забрав `ConfigureNotify` і знає новий розмір; з `update_idletasks` тут лягав би регіон під старий. `stop_resize` наприкінці накладає фінальний чистий регіон під точний розмір. `SetWindowRgn` **перебирає** володіння регіоном (сам видаляє попередній), тож `DeleteObject` потрібен лише коли виклик **не вдався** (ОС регіон не прийняла) — інакше витік GDI. `restype`/`argtypes` для `GetParent`/`CreateRoundRectRgn`/`SetWindowRgn`/`RedrawWindow` виставлені на рівні модуля, щоб 64-бітні HWND/HRGN не зрізалися до 32 біт;
- **ім'я файла в заголовку вписується під ширину** (`LogTrackerApp._fit_header_text`). `file_label` стоїть `sticky="nw"` (натуральна ширина), тож при малій ширині довге ім'я лізло під кнопки праворуч і кінець `.log` перекривався. Метод міряє реальним (масштабованим CTk) шрифтом `file_label._label` і, якщо повний текст не влазить у відстань до кнопок (`burger_button.winfo_x()`), обрізає хвіст ІМЕНІ, лишаючи `…` перед розширенням — `.log` завжди видно. Викликається в `on_error_found` і в `on_window_resize` (лише коли `event.widget is root`).

  > **Доступну ширину не можна брати з величин, які залежать від самої мітки — це храповик.** Обрізали текст → мітці треба менше місця → наступний перерахунок бачить меншу «доступну» ширину → обрізає ще. Спрацьовує на будь-якому `<Configure>`, навіть коли ширина вікна не мінялася (відкриття панелі налаштувань міняє лише висоту), тож ім'я з'їдалося по кілька символів за раз аж до самого `…`. Дві мірки, які цю петлю замикали і яких тут більше нема: `main_frame.grid_bbox(0, 0)` — під час обробки `<Configure>` він віддає ще не перераховану, ЗАПИТАНУ розкладку, тобто ширину колонки за натуральною шириною мітки (виміряно 611 замість реальних 1116); і `chrome = file_label.winfo_reqwidth() - measure(текст)` — `reqwidth` CTk-обгортки оновлюється лише наступним idle-циклом і порівнювався зі свіжим текстом (виміряно −392 і +432 замість реальних ~32 px іконки). Тепер у формулі лише **застосована** геометрія сусідів (`winfo_x` кнопки й мітки, праве `padx`) та ширина іконки з самого PhotoImage (`_header_icon_width`) — жодне з чисел від тексту не залежить. Ціна: на справжню зміну ширини вони відстають на один прохід розкладки, і наступна ж подія це виправляє (під час ресайзу `_apply_resize_frame` усе одно робить `update()` щокадру).

### Контур вікна (кути мають читатись як межа)

Безрамкове вікно не має рамки ОС, тож його межу малює сам застосунок. Раніше не малював зовсім: форму задавав лише Win32-регіон, а він **обрізає**, а не обводить. У світлій темі на білому тлі це було видно найгірше — паперовий фон заголовка (`#F5F4F1`) майже не відрізнявся від робочого столу, а біла картка (`#FFFFFF`) внизу не відрізнялася зовсім, тож нижні кути виглядали як діра без жодної межі.

Контур малює **`main_frame`** — він єдиний дістає до всіх чотирьох країв:

- `corner_radius = WindowHandler.CORNER_RADIUS` — рівно радіус регіону, щоб дуга CTk лягла **точно** на межу обрізання. Розбіжність тут не косметична: при більшому радіусі CTk між двома дугами лишається видимий клин фону канви (у light це `gray92` #EBEBEB — помітно сіріший за паперовий #F5F4F1; у dark — фон вікна, і кут читається як діра без межі), при меншому — регіон зрізає саму рамку. Тримається ця рівність не домовленістю двох констант, а тим, що регіон **питає радіус у цього самого віджета** (`_outline_radius_px` → `root._outline_frame`), тож розійтися вони не можуть навіть при зміні DPI на льоту;
- `border_width` / `border_color` — з ключів теми `window_border_width` / `window_border_color`.

**Контент мусить відступити від кутів.** Канва будь-якого дочірнього віджета непрозора, тож віджет, що дістає до кута, просто зафарбовує рамку саме там, де вона найпотрібніша. Дуга радіуса R відступає від кута по діагоналі на `R*(1 - 1/√2)` ≈ `0.293*R`; плюс сама рамка. Звідси `error_window._CONTENT_INSET` (для R=15 виходить 6) — його дістає `error_frame` як `padx` і **нижній** `pady`. Зверху лишається `1`: там межа з заголовком, а не з краєм вікна. Заголовку відступ не потрібен — мітка стоїть на `padx=10`/`pady=5`, кнопки на `padx=5`, і в зону дуги не заходять.

`_CONTENT_INSET` додається і до запасу в `apply_dynamic_min_height`: рівно стільки картка віддала нижньому відступу, тож без добавки запас під текст став би на стільки ж меншим.

**Регіон мусить ходити за розміром вікна — інакше кути «порожніють».** Регіон це жорсткий кліп фіксованого розміру: щойно вікно змінює розмір без нового `SetWindowRgn`, форма розходиться з вікном. Більше вікно обрізається по старій межі — прямий зріз без кутів і без рамки; менше лишається з квадратними кутами, і поверх них видно фон канви CTk (у light `gray92` #EBEBEB, помітно сіріший за паперовий фон). Раніше регіон оновлювали лише три місця — побудова вікна, `stop_resize` і відновлення з трея, — а геометрію міняють і інші: `_reapply_saved_geometry` (запобіжник від «замалого вікна» на старті) і сам CTk у `check_dpi_scaling` при зміні DPI, тобто **головний сценарій цього застосунку — реконект RDP**. Розсинхрон був і до появи рамки, але з `corner_radius` 6 клин був у кілька пікселів; з рамкою по краю та радіусом 15 він став очевидним на всіх чотирьох кутах.

Тепер регіон переставляє `WindowHandler.ensure_corner_region(root)` — по факту зміни стану `root._corner_region`, який виставляє `round_corners`. У стані **три** числа: `(width, height, radius)`. Радіус у ньому обов'язковий: при зміні DPI фізичний розмір вікна може лишитись тим самим, а радіус дуги — ні, і перевірка лише за розміром пропускала б рівно той випадок, який ламає кути.

Звідки він викликається:

- `_sync_corner_region` на `<Configure>` root — основний шлях. **Обидві прив'язки `<Configure>` на root (ця і дебаунс збереження геометрії в `LogTrackerApp`) ставляться з `add="+"`** — прив'язка без нього стирає всі попередні;
- `LogTrackerApp._ensure_on_screen` — тік раз на 2 с. Підстраховка: у полі регіон усе одно переживав зміну DPI зі старим радіусом, попри хендлер на `<Configure>`. Коштує це порівняння трьох чисел; `SetWindowRgn` іде лише коли реально розійшлося (виміряно: на спокої — жодного виклику).

**Ознака «жест ресайзу триває» — `_resize_scale`, а не `_resize_dir`.** Це загальне правило для всього ресайзу, а не деталь одного місця: `_resize_dir` означає лише «курсор зараз у зоні краю» — його виставляє `change_cursor` на **кожен `<Motion>`** там, тобто на просте наведення без кліку, і курсор, що пішов з вікна через край, лишає його виставленим назавжди (нових `<Motion>` уже нема, скинути нікому). Опорні точки жесту (`_start_*`) кладе тільки `start_resize`, і разом з ними — `_resize_scale`, який знімає `stop_resize`. Тож саме `_resize_scale` питають усі троє:

- `ensure_corner_region` — щоб під час жесту не смикати `SetWindowRgn` (регіон там веде `_apply_resize_frame` щокадру). З `_resize_dir` синхронізація регіону мовчки вимикалась після того, як курсор вийшов через край, — і саме так регіон переживав зміну DPI зі старим радіусом;
- `do_resize` — щоб не рахувати геометрію від опорних точок **попереднього** жесту. Без цього досить було провести мишею понад краєм, а тоді натиснути будь-де і смикнути мишею — і вікно стрибало в чужий розмір та позицію. Реальний сценарій: миша йде до кнопки Save панелі налаштувань низом вікна (там і кнопки, і зона краю), `start_resize` на самій кнопці виходить достроково, кнопка своєю ж командою ховає панель — і найменший порух із затиснутою кнопкою «ресайзив» вікно;
- `stop_resize` — щоб не писати ini і не перемальовувати кути на кожен звичайний клік.

**`event.widget` у цих хендлерах не завжди віджет.** Усі чотири прив'язані на `root`, тобто спрацьовують на подію з **будь-якого** віджета вікна — Tk виконує прив'язки по bindtags по черзі: віджет → клас → вікно → all. Якщо віджетна прив'язка встигла знищити сам віджет, до віконної доходить уже мертвий шлях, і Tkinter підставляє в `event.widget` сирий **рядок** замість об'єкта (`nametowidget` кинув `KeyError`). Рівно це роблять Save/Cancel панелі налаштувань: `CTkButton` кличе команду на `<Button-1>`, команда ховає панель разом із кнопкою — і наступний у ланцюгу `start_resize` падав на `AttributeError: 'str' object has no attribute 'winfo_toplevel'`. Тому root дістається через `WindowHandler._event_root(event)`, який на рядку віддає `None`, і хендлер просто виходить: клік по кнопці ресайзу все одно не починає, губити нема чого. Додаючи сюди новий хендлер на `root`, бери root тим самим способом.

`bind_resize_events` вішає **лише** resize-хендлери на `root`. Move-прив'язки (перетягування за заголовок) ставить `ErrorWindow.bind_events` напряму на `file_label` і `main_frame`, де є прямі посилання на віджети. Раніше `bind_resize_events` ще й дублював move, шукаючи заголовок за жорстко зашитим Tk-шляхом `".!ctkframe.!ctklabel"` — крихким до зміни ієрархії віджетів; ті самі хендлери одразу перезаписувались у `bind_events`, тож lookup був зайвий і його прибрано.

### Дії по заголовку і полю помилки

Прив'язки ставить `LogTrackerApp.__init__` (крім перетягування — його вішає `ErrorWindow.bind_events`):

| Віджет | Жест | Дія |
|---|---|---|
| заголовок | затиснути й тягнути | перемістити вікно (`WindowHandler.start_move`/`do_move`) |
| заголовок | подвійний клік | показати лог у Провіднику — **у теці джерела** |
| заголовок | **Ctrl** + клік | покласти **сам файл** у буфер + плашка «Copied!» одразу за іменем файла |
| поле помилки | подвійний клік | відкрити файл лога в застосунку за замовчуванням |
| поле помилки | **Ctrl** + клік | покласти **текст поля** у буфер + плашка «Copied!» по центру поля |

**Обидві дії по заголовку працюють з ОРИГІНАЛОМ із `source_directory`, а не з копією.** Шлях дає `LogTrackerApp._source_log_path()`: у заголовку стоїть ім'я файла з теки призначення (там працює трекер), але копія службова — її перезаписує кожен тік синхронізації, тож користувачу з неї користі нема. Ім'я при копіюванні не змінюється, тож оригінал шукається за `basename` у джерелі. Фолбеки, щоб жест не лишався без реакції: подвійний клік при зниклому оригіналі відкриває саму теку джерела, а якщо й вона недоступна (шляхи не задані, мережа відвалилась) — показує копію; Ctrl+клік у цьому разі копіює копію.

**Ctrl+клік по заголовку не «їде» вікном.** `<Control-Button-1>` специфічніший за `<ButtonPress-1>` (перетягування), і Tk обирає саме його — `start_move` не викликається. Але `<B1-Motion>` лишається прив'язаним, тож якщо посунути мишу не відпустивши кнопку, `do_move` рахував би зсув від **старої** опорної точки й смикнув би вікно. Тому обробник Ctrl+кліку сам кличе `WindowHandler.start_move(event, root)`.

**Буфер обміну — два формати, одна Win32-механіка.** `FileHandler._put_on_clipboard(format, payload)` тримає весь обмін із буфером, а публічні функції лише готують вміст:

- `copy_file_to_clipboard(path)` → **CF_HDROP**: у буфері сам файл, Ctrl+V у Провіднику/пошті дає файл, а не рядок;
- `copy_text_to_clipboard(text)` → **CF_UNICODETEXT**: показаний рядок помилки.

Усе на `ctypes`, без pywin32: зайва залежність у `requirements` і `hiddenimports` збірки заради кількох викликів не потрібна. `clip.exe` не годиться подвійно — уміє лише текст, та ще й у windowed-збірці блимає консоллю (саме так робив попередній `copy_file_path_to_clipboard`, який цей код замінив; він ніде не викликався). Tk-івський `clipboard_append` теж не годиться: Tk віддає вміст **за запитом**, а застосунок завершується через `os._exit(0)` — скопійоване зникало б із буфера разом із процесом.

Володіння пам'яттю: після успішного `SetClipboardData` блок належить **буферу** (система звільнить його сама, вміст переживає вихід із застосунку), тож `GlobalFree` тільки на **збоях** — інакше або витік, або зіпсований буфер. `OpenClipboard` може не вдатися (буфером володіє інший процес) — ретраїв нема свідомо: це головний потік Tk, підвисати в ньому не можна, користувач повторить кліком. Обидві функції повертають `bool`, і плашка показує «Copied!» або «Copy failed» за ним.

**Плашка (`ui/toast.py`, `Toast`).** Безрамкове вікно не має ані рядка стану, ані заголовка ОС, куди можна написати результат, а спливних повідомлень CTk не має зовсім. Плашка — **звичайний CTk-віджет поверх контенту (`place`), а не окремий Toplevel**. Перша версія була саме Toplevel над заголовком і поводилась як чужий об'єкт: висіла над рамкою вікна, не їхала з ним і не обрізалася його межами. Оверлей належить вікну — рухається з ним, ховається з ним у трей і не може опинитися «поруч».

**Місць показу два — за числом дій**, і кожна плашка з'являється там, куди клікнули. Віджети, відносно яких вона стає, задаються **один раз** у конструкторі (`ErrorWindow.create_widgets`), тож викликачу лишається сказати лише, яку дію він підтверджує:

- `show_in_header()` — у смузі заголовка, одразу за іменем файла. Ліва межа — правий край мітки (її ширина натуральна, `sticky="nw"`, тож правий край і є кінцем `.log`), права — кнопки заголовка: при довгому імені плашка **зсувається ліворуч і накриває хвіст назви**, аби кнопки лишались клікабельними (перевірено на мінімальній ширині вікна). `anchor="w"`, а `_PAD_Y` малий навмисно — плашка мусить уміщатися у висоту смуги заголовка, інакше звисала б у поле помилки;
- `show_in_field()` — точний центр поля помилки (`relx=rely=0.5`, `anchor="center"`): ані розміру плашки, ані масштабу DPI тут рахувати не треба, і центр лишається центром при ресайзі.

Контейнером щоразу є той віджет, у якому плашка стоїть (`main_frame` для заголовка, `error_frame` для поля), тож фон під нею — рівно той, що цей віджет рендерить; згасання від цього тільки виграє. Екземпляр **один на обидва місця** (`ErrorWindow.toast`): новий показ прибирає попередній, тож дві плашки одночасно не висять.

Плашка в заголовку з'являється в **зоні перетягування вікна**, тож `ErrorWindow` передає їй `bind_move` — той самий хелпер, яким прив'язки переміщення вішаються на `file_label` і `main_frame`. Без цього вона робила б у заголовку «мертвий» прямокутник, за який вікно не рухається. Для плашки в полі помилки він не потрібен — поле вікна не рухає.

**Згасання.** Прозорості в окремого віджета Tk немає (`-alpha` є лише у вікна, і це альфа **всього** вікна з теми), тож плашка розчиняється **змішуванням кольорів** із фоном контейнера — разом із текстом, інакше пляма зникла б, а напис лишився б висіти чітким. Фон під плашкою бере `_detect_color_of_master()` CTk: у темах контейнер часто `"transparent"` (у dark прозорі всі шари), і тоді видно дефолтний фон вікна CTk — та сама пастка, що з `settings_bg`/`context_menu_bg`. Значення **не** зобов'язане бути `#rrggbb`: CTk цілком віддає назву кольору Tk (`gray14`), і саме на перевірці формату згасання в dark мовчки вимикалось — тому обидва кольори переводить у числа `winfo_rgb`. Не вийшло визначити фон — плашка просто ховається без анімації.

> **Прогрес анімації — за реальним часом, не за номером кадру.** Крок таймера Windows ~15.6 мс, тож `root.after(16, …)` фактично спрацьовує приблизно раз на 31 мс: лічильник кадрів (`i / steps`) розтягував згасання **удвічі** проти заявленого — виміряно на знімках. Ratio рахується з `time.perf_counter()` (як тротлінг у `_apply_resize_frame`), тож тривалість витримується, а кадрів просто менше.

> **DPI в плашці.** Ручного масштабування тут майже нема — і це навмисно: `place`/`grid` CustomTkinter самі множать `x`/`y`/`padx`/`pady` на масштаб віджетів, а шрифт із теми масштабує сам `CTkLabel`. `relx`/`rely` CTk не чіпає й не мусить: це частки розміру контейнера, а `winfo_*`, з яких вони рахуються, фізичні і в чисельнику, і в знаменнику — масштаб скорочується. Вручну множимо лише зазор `_GAP`, бо він заданий логічним, а порівнюється з фізичними `winfo_*`; масштаб — з того самого `WindowHandler._window_scale`. Скруглення дає нативний `corner_radius` CTk, тобто Win32-регіон (`round_corners`) тут не потрібен.

### Теми

`ThemeManager.load_theme(name)` робить `importlib.import_module(f"themes.{name}_theme")` і читає з модуля `THEME_SETTINGS`. Доступні: `dark`, `light`, `graphite`.

Щоб додати тему: створити `themes/<name>_theme.py` з `THEME_SETTINGS` і додати пункт у список `themes` в `ContextMenu._build_items()`. Іконка пункту не обов'язкова: `get_ctk_image` на відсутньому файлі віддає `None`, і рядок будується без картинки — колонка іконки лишається на місці, тож вирівнювання не з'їжджає.

**Контракт:** усі три теми зараз мають **ідентичний набір ключів**. `ThemeManager.update_widgets_theme()` звертається до ключів напряму, без `.get()` — відсутній ключ дасть `KeyError` при перемиканні теми. Додаючи ключ, додавай його в усі теми.

Додаючи новий стилізований віджет, треба змінити **два** місця: `ErrorWindow.create_widgets()` (початкове створення) і `ThemeManager.update_widgets_theme()` (перемикання на льоту), плюс зареєструвати віджет у словнику `widgets_to_update`.

**`window_border_color` / `window_border_width` — це контур самого вікна**, а не якогось віджета всередині: його малює `main_frame` (див. «Контур вікна»). Тому в `update_widgets_theme` запис `main_frame` конфігурує не лише `fg_color`, а й обидва ці ключі — інакше перемикання теми лишало б рамку кольором старої. У світлій темі колір — найтемніша сходинка драбини рамок (`#E6E4DF` картка → `#D6D4CD` поля → `#C9C6BF` край вікна); у dark/graphite береться колір бордера полів, на крок світліший за фон вікна.

**Виняток — панель `Path settings` (`SettingsPanel`).** Вона стилізується групою ключів `settings_*` (`settings_bg`, `settings_text_color`, `settings_font`, `settings_entry_fg_color`, `settings_entry_border_color`, `settings_button_fg_color`, `settings_button_hover_color`, `settings_button_text_color`), але **не** проходить через `update_widgets_theme`: її віджети існують лише поки панель відкрита, а `update_widgets_theme` звертається до словника напряму. Стиль читається з `current_theme_data` при побудові, а зміну теми на льоту (панель не модальна — бургер-меню поруч) панель ловить власним `apply_theme()`, який кличе `LogTrackerApp.toggle_theme`. Значення `settings_*` виведені з палітри кожної теми, щоб контролі належали тому самому вікну (фон = фон вікна теми, кнопки = синій акцент). Ключі підпадають під контракт вище — вони є в усіх трьох темах. `settings_font` навмисно дорівнює `error_textbox_font`, щоб текст налаштувань і поля помилки мали однаковий кегль. `settings_bg` окремим віджетом більше не малюється (сама панель прозора й показує фон `main_frame`), але лишається чинним описом того, що вікно реально рендерить, — див. пастку фону в dark нижче.

**Так само поза `update_widgets_theme` — плашка «Copied!» (`Toast`).** Ключі `toast_bg`, `toast_border_color`, `toast_text_color`, `toast_font` читаються з `current_theme_data` при **кожному показі**, тож плашка завжди в актуальній темі; реєструвати її в `widgets_to_update` нема сенсу — вона живе ~1.4 с і в момент перемикання теми просто не існує. Ключі підпадають під контракт вище — є в усіх трьох темах.

**І так само — бургер-меню (`ContextMenu`).** Група `context_menu_bg`, `context_menu_fg`, `context_menu_active_bg`, `context_menu_active_fg`, `context_menu_border_color`, `context_menu_separator_color`, `context_menu_accent_color`, `context_menu_muted_fg`, `context_menu_font` читається при **кожному відкритті**: картки будуються заново, а перемкнути тему, поки меню відкрите, неможливо — вибір теми сам його й закриває. Ключі підпадають під контракт вище.

Меню — **піднята поверхня**, як і плашка: воно висить над вікном, має власний контур і скруглені кути, тож `context_menu_bg` дорівнює `toast_bg` кожної теми (dark `#2b2c2f`, graphite `#42464d`, light `#FFFFFF`), а не фону вікна. `context_menu_border_color` — той самий волосяний контур, що окреслює вікно й плашку (у light узято на сходинку темніше, `#D6D4CD`: меню лягає на довільний вміст екрана, і його межа має читатись певніше за внутрішній сепаратор). `context_menu_active_bg` — синій/індиго акцент, той самий, що `*_button_hover_color`. `context_menu_accent_color` дорівнює `header_label_text_color`: позначка «✓» на поточній темі говорить тим самим акцентом, що ім'я файла в заголовку. `context_menu_muted_fg` — приглушений колір службової стрілки «›», яка не має конкурувати з написом. `context_menu_font` дорівнює `error_textbox_font` (той самий кегль, що в тексті помилки), і CTk масштабує його сам.

Плашка говорить **мовою поверхонь** теми, а не заливкою акцентом: `toast_bg` — на крок світліший за те, що реально рендерить заголовок (dark `#2b2c2f` над `#242424`, graphite `#42464d` над `#383b40`, light `#FFFFFF` над паперовим `#F5F4F1`), тобто «піднята» поверхня; `toast_border_color` — волосяна лінія кольору бордера полів, яка й окреслює плашку, бо фон навмисно близький до фону заголовка; а колір несе `toast_text_color`, і то **рівно той самий акцент, що `header_label_text_color`** — ім'я файла й підтвердження поруч звучать в один голос. Перша версія заливала плашку акцентом (`#2d436e`) і в dark виглядала чужою: суцільним кольором там не залито нічого, акцент живе лише як ховер. Виміряний крок поверхні — 12–16 рівнів на канал у кожній темі. `toast_font` на пункт менший за `header_label_font` і жирний: це короткий службовий сигнал, він не має конкурувати з вмістом вікна.

> **Пастка фону в dark (стосується `settings_bg`).** У світлій/graphite цей ключ дорівнює **конкретному** `main_frame_fg_color` — і збіг із головним вікном точний. Але в **dark** `main_frame_fg_color = "transparent"`: усі шари головного вікна прозорі, тож воно показує **дефолтний фон вікна CTk для Dark — `gray14` (#242424)**. Тому в dark `settings_bg` = `#242424`, а **не** світліший `#2b2c2f` — інакше смуга налаштувань у dark була б помітно світліша за решту вікна (це вже було, ще коли вона була окремим діалогом: перші версії брали #2b2c2f і не збігалися). Сама панель тепер малюється прозорою й показує фон `main_frame` напряму, тобто виходить на те саме значення вже за побудовою; ключ лишається чинним описом того, що вікно рендерить. Правило: фон дочірньої поверхні, яка має **зливатися** з вікном, дорівнює тому, що вікно **реально рендерить**, а не абстрактному «темному». Те саме стосується `_detect_color_of_master()` у `Toast`.
>
> Це правило не поширюється на поверхні, які навмисно **підняті** над вікном — плашку (`toast_bg`) і бургер-меню (`context_menu_bg`). Вони мають власний контур і скруглені кути, тобто читаються як окремий шар, а не як продовження вікна; їхній фон — на крок світліший за те, що рендерить вікно. `context_menu_bg` у dark свого часу вже було зведено до `#242424` — але тоді меню було пласким `tk.Menu` без будь-якої межі, і збіг фонів був єдиним, що прив'язувало його до вікна.

### Бургер-меню (власний попап, а не `tk.Menu`)

Меню будує `ui/context_menu.py`: безрамковий `Toplevel` зі **скругленою карткою CTk** усередині — рядки з ховером-пігулкою, іконками, підменю збоку і позначкою «✓» на поточній темі.

Нативний `tk.Menu`, який тут стояв раніше, давав системний вигляд, що не належав жодній темі, і кожна дрібниця вимагала обхідного шляху: `activeborderwidth=0` проти світлої облямівки навколо меню й активного пункту, явний `background` у кожного `add_separator()` проти білої 3D-гравірованої лінії (Tk брав під неї системний SystemButtonFace), кегль, **скопійований з поля помилки** (Tk не бачить per-monitor DPI при awareness V2, тож масштабувати шрифт доводилося вручну), іконки — окремим `tk.PhotoImage` з ручним множником DPI. Скруглених кутів, ховера-пігулки й позначки стану він не давав узагалі. Тепер усе це робить CTk своїми віджетами, а кольори приходять із тих самих ключів `context_menu_*`.

Структура: `ContextMenu` (контролер) → `_MenuPopup` (одна картка) → `_MenuRow` (`[іконка] [текст] [›/✓]`). Ланцюг не глибший за два рівні: головна картка і підменю Theme.

Що тут навмисне:

- **Вікно — звичайний `tk.Toplevel` (`_MenuWindow`), а не `CTkToplevel`.** CTkToplevel у конструкторі робить `withdraw()` + `update()` + відкладений `deiconify()` заради кольору заголовка і через 200 мс ставить свою іконку — для попапа без заголовка це блимання і TclError у `after`-колбеку, якщо меню закрили раніше. До того ж CTkToplevel масштабує `geometry()` у **логічні** одиниці, а попап позиціонується від `winfo_rootx()` кнопки, тобто у **фізичних**; звичайний Toplevel лишає геометрію в тих самих одиницях, що й усі `winfo_*`.
- **Дві порожні заглушки `block_update_dimensions_event` / `unblock_update_dimensions_event`** у `_MenuWindow` — не косметика. `ScalingTracker` CTk вважає **кожен** Toplevel із CTk-віджетами окремим «вікном зі своїм DPI» і при зміні масштабу кличе в нього ці методи (вони є лише в CTk-вікон). Без заглушок зміна DPI з відкритим меню (реконект RDP — головний сценарій застосунку) кинула б `AttributeError` усередині `check_dpi_scaling`, і цикл **перестав би перезапускатися**: CTk більше не помічав би зміни DPI до перезапуску процесу.
- **Масштаб попапа береться з головного вікна** (`_adopt_window_scaling` кладе значення з `ScalingTracker.window_dpi_scaling_dict[root]` **до** створення першого CTk-віджета). Інакше CTk визначив би його сам через `MonitorFromWindow` на ще не показаному HWND — тобто за DPI первинного монітора, і на конфігурації з різним DPI меню було б іншого кегля, ніж вікно, з якого його відкрили.
- **Запис попапа з обох словників `ScalingTracker` прибирається в `destroy()`.** CTk чистить звідти лише колбеки віджетів, а ключ мертвого вікна лишається назавжди — меню ж відкривають десятки разів за сесію, і цикл `check_dpi_scaling` обходив би щосекунди дедалі довший список.
- **Прозорість — та сама, що у вікна** (`window_alpha` теми: 0.9 у dark/graphite, 1 у light). Меню висить над напівпрозорим вікном, і суцільно непрозора картка читалася б як чужий, «твердіший» об'єкт. Значення береться на кожне відкриття, тож після зміни теми меню одразу відповідає вікну. Наслідок, який не лікуємо: `check_dpi_scaling` CTk на зміні DPI виставляє `-alpha` в `1` **усім** зареєстрованим вікнам, зокрема відкритому попапу (для головного вікна це лікує `_ensure_on_screen`) — попап живе секунди, і наступне відкриття вже правильне.
- **Кути — той самий `WindowHandler.round_corners`, що й у головного вікна.** Попап кладе на себе `_outline_frame` (картка) і `_outline_radius` (10 замість 15 у вікна), звідки `_outline_radius_px` бере логічний радіус. Регіон і намальована CTk дуга лишаються одним числом за побудовою. Регіон накладається **після** `deiconify()`: wrapper-HWND, якому його віддають, Tk створює лише при мапінгу вікна.
- **Прив'язки — на самому Toplevel, а не на рядках.** Bindtags дочірнього віджета містять шлях його toplevel, тож подія з будь-якої мітки доходить до попапа, і рядок визначається **позицією** курсора. Це заразом прибирає класичне мигання ховера: `<Enter>`/`<Leave>` на віджетах дають Leave+Enter на межі іконки й тексту, хоча курсор рядка не залишав. З тієї ж причини `<Leave>` довіряє лише координатам (`contains`), а курсор «повз рядки» (сепаратор, відступ) підсвітку не знімає.
- **Грабів (`grab_set`) немає.** Глобальний граб перенаправив би події вікну, що його тримає, і підменю (окремий Toplevel) перестало б отримувати рух миші. Клік повз меню ловиться через `<FocusOut>`: попап бере фокус (`focus_force`, перевірено — його wrapper стає foreground-вікном), тож будь-який клік по іншому вікну, своєму чи чужому, фокус забирає. Рішення відкладається на 60 мс і звіряється з `focus_displayof()`, бо FocusOut приходить і тоді, коли фокус перейшов у **своє ж** підменю.
- **Гард на повторне відкриття (`_REOPEN_GUARD_S`).** Клік по бургеру при відкритому меню приходить **після** FocusOut, який його вже закрив; без гарда меню миттєво відкрилося б знову замість тумблера.
- **Підменю закривається із затримкою (`_SUBMENU_CLOSE_MS`)**, коли курсор іде на інший рядок: дорога до підменю праворуч часто йде по діагоналі, через сусідні рядки, і без затримки воно зникало б просто по дорозі до себе.
- **Пункти будуються на кожне відкриття** — позначка поточної теми і кольори залежать від стану, який міг змінитися. Це ~50–80 мс на побудову (виміряно), тобто в межах кліку.
- **Сепаратор один — перед Exit.** Старе меню розділяло ним кожен пункт, тобто читалося як три групи по одному; тут відділене саме те, що завершує роботу застосунку.

### Ресурси і PyInstaller

`PathUtils.resource_path()` (`utils/path.py`) резолвить шляхи через `sys._MEIPASS` у зібраному вигляді і `os.path.abspath(".")` у dev. У `ui/ui_assets.py` є **дубль** тієї самої функції; там же `APP_ICO_PATH` уже резолвнутий, а решта констант — відносні шляхи, які резолвляться вже у викликачів (`ImageManager`, `TrayManager`). Непослідовно, але саме так це працює.

**Спільна іконка застосунку.** Один дизайн («жук», акцентний синій `#5f8dfc` на прозорому) слугує всім чотирьом місцям, у двох форматах із одного джерела (`ui_assets.APP_ICON_PATH` / `APP_ICO_PATH`):

- `src/app_icon.png` — **256×256** майстер. Іде в шапку вікна (`ErrorWindow` → `get_ctk_image(size=(16,16))`) і в іконку трея (`TrayManager`). Обидва **самі зменшують** його під DPI (CTkImage множить логічний розмір на масштаб вікна; трей віддає Windows), тож джерело навмисно високороздільне — зменшення LANCZOS чітке на будь-якому DPI, тоді як старий 16×16 `bug2.png` на 150–200% розмивався (та сама пастка, що з іконками меню).
- `src/app_icon.ico` — **мультирозмірний** (16, 20, 24, 32, 40, 48, 64, 128, 256). Іде в `iconbitmap` головного вікна і в іконку `.exe` (`logger.spec`). Windows сам бере потрібний розмір під DPI таскбара/alt-tab. Кожен кадр — окреме LANCZOS-зменшення з високого супер-семплу, файл у стандартному layout (малі BMP, 256 PNG), який Tk `iconbitmap` приймає.

Обидва файли генерує `tools/generate_app_icon.py` (не рантайм-код застосунку) — малює жука з 8× супер-семплом і зменшує LANCZOS. Щоб перемалювати іконку — правити дизайн у цьому скрипті й запустити `python tools/generate_app_icon.py`: він перезапише обидва формати з одного майстра. Замінюючи майстер-PNG вручну, тримай його **≥128px** (краще 256), інакше повернеться розмиття на high-DPI.

`logger.spec` виводить два списки глобами, тож нові файли підхоплюються самі:

- `datas` — глоб по `src/*` (іконки + ini) у цільову теку `'src'`;
- `hiddenimports` — глоб по `themes/*_theme.py`. **Обов'язковий**: `ThemeManager.load_theme` тягне теми через `importlib.import_module`, статичний аналіз PyInstaller такий імпорт не бачить. Без цього exe падає на старті з `ModuleNotFoundError: No module named 'themes'`.

Збірка **one-file** і windowed: `EXE` вкладає `a.binaries` + `a.datas` прямо в себе (без `COLLECT`), тож на виході **один** `dist/logger.exe` (~18 МБ), а не тека `dist/logger/` з `_internal`. `console=False`, іконка exe — `src/app_icon.ico`. У рантаймі PyInstaller розпаковує вкладене в тимчасову `%TEMP%\_MEIxxxxx\` і ставить туди `sys._MEIPASS`; ця тека створюється на старті й видаляється при виході (тому старт +1–3 с проти onedir). Усе записуване (конфіги, лог) навмисно виноситься в `%LOCALAPPDATA%` — див. нижче.

**Куди пишуться конфіги в зібраному вигляді.** Записувані конфіги (`config.ini`, `window_config.ini`) у зібраному вигляді лежать **не** поруч з exe, а в `%LOCALAPPDATA%\LogTracker\` — поряд із логом (`rthook_logfile`). Шлях будує `PathUtils.user_config_path(filename)`: якщо `sys.frozen` — віддає `%LOCALAPPDATA%\LogTracker\<filename>`, інакше (dev, `python logger.py`) — старий `src/<filename>`, який у git. `constants.CONFIG_PATH`, `config_manager.CONFIG_FILE_WINDOW`, `window_handler.CONFIG_FILE_WINDOW` і `theme_manager.config_path` усі йдуть через цей хелпер.

**Сідування.** При першій появі (файлу ще нема в `%LOCALAPPDATA%`) `user_config_path` копіює bundled-версію з ресурсів (`sys._MEIPASS\src\<filename>`) у записувану теку, щоб дефолти (`word`, `file_extension`, теми) не загубилися. Розпаковані в `%TEMP%\_MEIxxxxx\src\` ресурси лишаються **read-only еталоном** — застосунок їх не переписує (та й не було б сенсу: ОС прибирає цю теку при виході).

Шляхи в сіді (`source_directory`/`destination_directory`) навмисно **порожні**: на новій машині їх задає користувач через «Path settings», а до того застосунок показує підказку (див. «Перший запуск і незадані шляхи»). `word`/`file_extension` у сіді збережені. У **dev**-режимі (`python logger.py`) читається саме `src/config.ini`, тож після очищення сіду перший dev-запуск теж покаже підказку, доки шляхи не задано вручну.

Причина переносу: `sys._MEIPASS` у зібраному вигляді — **не** постійне місце. У колишній однотечній (`COLLECT`) збірці він указував на `dist/logger/_internal` усередині теки встановлення — під `C:\Program Files` запис туди впав би без адмін-прав, а перевстановлення затерло б налаштування. У теперішній one-file збірці він указує на тимчасову `%TEMP%\_MEIxxxxx`, яку ОС видаляє при виході, — писати конфіги туди означало б **втрачати їх щозапуску**. `%LOCALAPPDATA%` записуваний завжди, спільний для обох режимів і переживає перевстановлення.

### Логування в зібраному вигляді

`rthook_logfile.py` — PyInstaller runtime hook (`runtime_hooks` у spec), який перенаправляє `sys.stdout` і `sys.stderr` у файл:

```
%LOCALAPPDATA%\LogTracker\logger.log     — поточний запуск
%LOCALAPPDATA%\LogTracker\logger.log.1   — попередній
```

Активується строго за умовою `sys.frozen and sys.stdout is None`, тобто **лише** в windowed-збірці. Запуск із сирців (`python logger.py`) і збірка з `console=True` працюють як раніше — вивід у консоль.

Деталі, які не варто ламати при правках хука:

- **`buffering=1` (line buffering) обов'язковий** — `LogTrackerApp.on_closing` завершується через `os._exit(0)`, який не скидає буфери Python; при блоковій буферизації хвіст лога губиться.
- **Ліміт `MAX_BYTES` (5 МБ)** — `WindowHandler.do_resize` друкує ~6 рядків на кожну подію руху миші, без обмеження файл росте необмежено. Після ліміту запис тихо припиняється, застосунок працює далі.
- Файл у UTF-8. `Get-Content` у Windows PowerShell 5.1 читає в ANSI і покаже кирилицю кракозябрами — читати `Get-Content ... -Encoding UTF8`.
- Весь хук обгорнутий у `try/except`, щоб збій логування не завалив старт.

Завдяки цьому виняток на старті потрапляє у файл. Без хука `console=False` дає лише діалог «Unhandled exception in script» без тексту — жодної діагностики.

Усі ресурси `src/` (іконки + ini) тепер у git. `ImageManager.get_ctk_image()` при відсутньому файлі повертає `None` мовчки, а `TrayManager` переходить на згенеровану `create_image()`-заглушку — тобто пропалий ассет не дає помилки, лише порожню іконку. Якщо іконки зникли, шукати треба саме тут.

**Роздільність іконок бургер-меню (не занижувати).** Іконки меню (`settings_icon.png`, `exit_icon.png`, `theme.png`, `moon2.png`, `day2.png`, `graphite.png`) зберігаються у **128×128**. `_MenuRow` просить у `ImageManager.get_ctk_image` **логічний** розмір `(16,16)`, а CTkImage сам зменшує джерело до `16 × scale` фізичних px (32 при 200% DPI, 40 при 250%). Майстер 128px тому **завжди зменшується** — на будь-якому DPI чітко. Раніше джерела були 16×16: при DPI >100% той самий resize **збільшував** їх (16→32), а збільшення растру завжди розмите — на high-DPI (основний RDP/Retina-сценарій) іконки були м'які. Правило: замінюючи іконку меню, клади файл **≥64px, а краще 128px**; 16×16 повертає розмиття.

Ручного масштабування іконок меню більше нема: воно було потрібне лише нативному `tk.Menu` (Tk не бачить per-monitor DPI при awareness V2, тож `ImageManager` тримав окремий метод `get_tk_photo_image` з явним множником). Разом із переходом меню на CTk той метод видалено — усі зображення застосунку тепер ідуть одним шляхом, через `get_ctk_image`.

## Життєвий цикл вікна

`WM_DELETE_WINDOW` перевизначено на `TrayManager.minimize_to_tray` — хрестик **не закриває** застосунок. Реальний вихід — `app.on_closing()` (пункти «Exit» у бургер-меню та в меню трея), який зупиняє observer, зберігає геометрію і завершується через `os._exit(0)`.

`is_window_open` — прапорець стану; коли він `False` і приходить нова помилка, `on_error_found` сам піднімає вікно з трею.

Меню трея будується заново при кожному згортанні (`minimize_to_tray`), запускається через `run_detached()`.

### Підвищення іконки трея (Win11 «always show»)

`utils/tray_promote.py` → `promote_tray_icon()` виставляє іконку застосунку в треї як **завжди видиму**, а не сховану в overflow (зона за шевроном `^`, куди Windows 11 кладе іконки нових застосунків за замовчуванням). Викликається **один раз** на старті в `logger.py` → `run()`, **до** першого `minimize_to_tray` — тоді прапорець уже стоїть, коли Explorer додає іконку.

Офіційного API для цього немає — Microsoft віддає рішення користувачу. Механізм **недокументований**: Explorer тримає стан кожної іконки в `HKCU\Control Panel\NotifyIconSettings\<id>`, серед значень — `ExecutablePath` і `IsPromoted` (DWORD: `1` = завжди показувати, `0`/відсутнє = overflow). Функція обходить підключі, знаходить свій за збігом `ExecutablePath` із `sys.executable` (`normcase`) і ставить `IsPromoted=1`. Усе в `try/except`, будь-який збій — тихий no-op.

Свідомі обмеження (не «баги» — не «виправляти»):

- **Тільки frozen + Win11.** У dev (`sys.executable == python.exe`) і на Win10 (там ключ інший — зашифрований блоб `IconStreams`) — тихо нічого не робить.
- **Найперший запуск нового exe — ще в overflow.** Підключ `<id>` — хеш від Explorer, наперед його не відтворити; він з'являється лише **після** першого показу іконки. З 2-го запуску й далі — завжди видима.
- **Прив'язка до шляху exe.** Перенесення/перезбірка exe в іншу теку = для Windows новий застосунок, видимість скидається. Тому підвищуємо **щоразу** на старті — код сам «лікує» новий шлях. Наслідок: якщо користувач свідомо сховає іконку через налаштування, наступний запуск поверне її.

## Windows-only

`ctypes.windll` викликається без охорони платформи в `utils/rdp.py`, `ui/window_handler.py`, `pin.py`. Тільки `logger.py` перевіряє `sys.platform`. Крос-платформні гілки є лише у `FileHandler` (відкриття файлу, буфер обміну, показ у провіднику).

## Мертвий код

Не редагувати без потреби, не брати за приклад:

- `pin.py` — окремий демо-скрипт `RoundedWindow`, ніде не імпортується;
- `build/`, `dist/` (від `pyinstaller logger.spec`) та `output/` (від auto-py-to-exe) — артефакти збірки, у `.gitignore`.

## Мова

Коментарі й повідомлення в коді змішані: українська, російська, англійська. Логування — виключно `print()`, без модуля `logging`. Дотримуйся стилю файлу, який редагуєш.

`logger.py` на старті виставляє `errors="replace"` для `sys.stdout` / `sys.stderr`. Без цього `print()` з кирилицею падав з `UnicodeEncodeError` на консолі в cp1252/cp866 — найчастіше всередині `except`-гілки, через що обробник помилки сам ставав помилкою і ховав початкову причину. Кодування навмисно не підміняється на utf-8: у консолях зі старою кодовою сторінкою це дало б кракозябри. У windowed-збірці вивід перехоплює `rthook_logfile.py` і пише в utf-8 без втрат.
